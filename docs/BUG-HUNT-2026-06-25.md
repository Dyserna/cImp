# cctts bug hunt — confirmed findings

Run: 14 Opus finders + adversarial Opus verification. 68 candidates -> 37 confirmed, 31 refuted.

## 1. [HIGH] Changing a remote backend's auth token to a different non-empty value is silently ignored (stale token reused)
- **File:** `src-tauri/src/offload/service.rs`  (lines 559-583, 842-844)
- **Scope/Category:** offload-core / bad-assumption   **Confidence:** high
- **Problem:** resolve_remote reuses a cached RemoteBackend handle when `h.base_url() == base_url.trim_end_matches('/')` AND `remote_sig(h, is_cloud) == sig`. Both signatures encode only the *presence* of an auth token as a bool, not its value: sig uses `auth_token.is_empty()` and remote_sig uses `h.auth_token().is_none()`. If the user edits a backend's bearer token from one non-empty value (e.g. an expired/rotated key) to a different non-empty value, both bools stay false, the signatures match, and the cached handle is reused with the OLD token baked into its reqwest client/auth.
- **Why it triggers:** RemoteBackend stores auth_token at construction; resolve_remote only rebuilds it when base_url or the presence-bool changes. A rotated cloud API key (very common) therefore keeps failing with 401/403 until the base_url changes or the app restarts, with no indication why. The PoolEntry.auth_token returned to the agent loop is taken from the fresh config string, but the *health/props probe* (handle.health_check / refresh_props) uses the stale-token client, so the backend can also be marked unready using the wrong credential.
- **Suggested fix:** Include a hash/fingerprint of the actual auth_token (not just is_empty) in both `sig` and `remote_sig`, or compare h.auth_token() against the new token value directly so any token change forces a rebuild.

## 2. [MEDIUM] Selection "done" sentinel dropped on a full state-signal channel
- **File:** `src-tauri/src/audio/playback.rs`  (lines 383-398)
- **Scope/Category:** audio-tts / edge-case   **Confidence:** high
- **Problem:** When the read-along's end-of-read sentinel is emitted, `state_signals.try_send(TtsSelectionProgress{index==count})` is fired with `let _ =` and `pending_done = None` is then set unconditionally (line 394), regardless of whether the send returned `Err(Full)`. If the bounded `state_signals` channel (capacity 64, main.rs:148) is momentarily full at that tick, the done edge is silently lost and never retried.
- **Why it triggers:** The audio thread is the only servicer of this channel under bursty playback/state edges, so transient `Full` is realistic. Losing the `index==count` sentinel means the frontend selection highlight is never cleared after the read finishes — it sticks on the last sentence. Note the Started/Stopped avatar edges in the same loop (lines 430-454) deliberately retry on `Full`; the progress/done edges do not, so this is an inconsistency, not an intended trade-off.
- **Suggested fix:** Only clear `pending_done`/advance `last_front` when `try_send` returns `Ok` (or `Closed`); on `Full`, keep the state and retry on the next poll tick, mirroring the Started/Stopped handling.

## 3. [MEDIUM] Lost-update race: settings_update can clobber a concurrent tab add/remove (and vice versa)
- **File:** `src-tauri/src/ipc/tab_lifecycle.rs`  (lines 207-222)
- **Scope/Category:** ipc / race   **Confidence:** high
- **Problem:** All tab mutations use the read-modify-write pattern `let mut snap = state.settings.current(); snap.tabs.push(...); state.settings.set(snap);`. SettingsHandle::set replaces the whole Settings wholesale (`*g = new`, broadcaster.rs:84). The lifecycle_serializer only serializes the lifecycle commands against EACH OTHER. settings_update (commands.rs:661), set_active_tab (commands.rs:600), save_layout (layout.rs:28), save_layout_preset, etc. do NOT take lifecycle_serializer and also do current()->mutate->set().
- **Why it triggers:** The Settings window is a separate webview that can invoke settings_update at any moment. If the user toggles any setting there while the main window is creating/closing a tab, settings_update reads a snapshot taken before snap.tabs was updated, then set()s it back — dropping the newly created tab (or resurrecting a closed one) from persisted settings. The registry and on-disk settings then disagree. Same hazard between save_layout/set_active_tab and a tab mutation.
- **Suggested fix:** Either route every settings mutation through the lifecycle_serializer, or give SettingsHandle a `mutate(|s| ...)` API that holds the inner Mutex across the read-modify-write so updates compose instead of clobbering.

## 4. [MEDIUM] is_read_class can be bypassed: a write tool named with no listed verb (e.g. localized/odd naming) is exposed to the local worker
- **File:** `src-tauri/src/offload/mcp_host.rs`  (lines 152-180)
- **Scope/Category:** offload-server-mcp / security   **Confidence:** medium
- **Problem:** is_read_class() is a verb-blocklist over English leading verbs. A third-party MCP server can advertise a mutating tool whose name does not start with any listed verb (e.g. `fs_overwrite` is caught by HARD `overwrite`, but `file_replaceContents` → segment_words gives [file, replace, contents] and `replace` IS hard — caught; however `git_amend`, `db_upsert`, `node_destroyAll`→destroy caught; but `repo_force` / `branch_force` / `config_persist` / `state_flush` / `cache_evict` / `task_cancel` / `job_abort` are NOT in any list and pass as read-class). The code's own doc admits this is best-effort, but several common mutating verbs (persist, flush, evict, cancel, abort, force, amend, upsert, sync, fetchAndWrite) are absent, so genuinely destructive tools can be advertised to the local model.
- **Why it triggers:** The offload worker is documented as read-only and this filter is the boundary for third-party MCP tools (the filesystem server is separately confined, but git/db/custom servers rely on this name filter). A tool like `branch_force` or `state_flush` slips through and the local model can invoke it. The mitigation note says filesystem is the real boundary, but non-filesystem mutating servers have no other guard.
- **Suggested fix:** Invert the policy for third-party servers: default-deny and only allow an explicit read-verb allowlist (get/list/read/search/fetch/show/describe/...), or require the server config to opt tools in, rather than blocklisting an open-ended set of write verbs.

## 5. [MEDIUM] dangerous_args git guard misses the combined short form and other code-exec subcommands
- **File:** `src-tauri/src/offload/tools/run_command.rs`  (lines 82-102)
- **Scope/Category:** offload-tools / security   **Confidence:** high
- **Problem:** The git hardening blocks `-c`, `-C`, and `--config-env/--exec-path/--upload-pack/--receive-pack`. It does NOT block `git config` (the subcommand, which can write core.pager/core.sshCommand/alias.*=!cmd into the repo's .git/config, after which a later allowlisted `git log`/`git diff` in the same root triggers arbitrary command execution via the pager/ssh hooks), nor `--no-pager` vs pager abuse, nor `-c` is checked but git also honors the GIT_* env and `--git-dir`/`--work-tree` (escape the root). Because offload runs as a sequence of separate run_command calls in a persistent allowed root, a `git config core.pager='!sh -c ...'` call writes state that a subsequent `git log` executes.
- **Why it triggers:** Two-step exploit: call 1 `git config core.pager '!malicious'` (or alias), call 2 `git log` — the second spawns the pager, achieving arbitrary command execution while every individual call passed the bare-name + allowlist + flag checks. The flag denylist only inspects argv of a single invocation and ignores persisted config writes.
- **Suggested fix:** Refuse the `git config` subcommand (and `--git-dir`/`--work-tree`) in dangerous_args, or force `-c core.pager=cat -c core.sshCommand=...`-style neutralization / set GIT_PAGER=cat and disable config-driven hooks when spawning git.

## 6. [LOW] Selection begin-edge progress dropped on full channel and never re-emitted
- **File:** `src-tauri/src/audio/playback.rs`  (lines 366-377)
- **Scope/Category:** audio-tts / edge-case   **Confidence:** high
- **Problem:** The per-chunk "now playing" progress edge uses `let _ = state_signals.try_send(...)` but updates `last_front = Some(f)` (line 369) before the send. If that send returns `Err(Full)`, `last_front` has already advanced, so the edge is never re-emitted for that chunk.
- **Why it triggers:** Same backpressure path as the done-sentinel bug. A dropped begin edge means the frontend never highlights that particular sentence (highlight skips a chunk) even though its audio plays. Low severity because it only affects the read-along highlight visuals, not audio.
- **Suggested fix:** Advance `last_front` only after a successful (or Closed) `try_send`; on `Full`, leave `last_front` unchanged so the edge retries next tick.

## 7. [LOW] Mark/sink length invariant can desync when a source drains in the same poll tick as an enqueue
- **File:** `src-tauri/src/audio/playback.rs`  (lines 301-359)
- **Scope/Category:** audio-tts / race   **Confidence:** high
- **Problem:** `marks` is kept in lock-step with `sink.len()` by popping `prev_len - len` marks whenever `len < prev_len`. But a single loop iteration can both enqueue (push one mark, append one source) and observe a source that drained since the last tick. If one source drained AND one was enqueued, the net `sink.len()` is unchanged, so `len < prev_len` is false and no mark is popped — leaving a stale finished chunk's mark at the front of `marks`.
- **Why it triggers:** After this, `marks.front()` points at an already-finished chunk, so the loop re-emits a begin edge for a chunk that is done, and the deque stays permanently offset by one relative to the sink FIFO for the rest of that read. Triggers only when a chunk finishes within the exact 50ms window in which an Enqueue command is also processed, so it is narrow, but it does break the documented `marks.len() == sink.len()` invariant.
- **Suggested fix:** Compute the drain delta against the length captured BEFORE processing the Enqueue (snapshot `sink.len()` at the top of the loop before appending), or track appended-this-tick count and reconcile, so a same-tick append cannot mask a drain.

## 8. [LOW] Paused playback keeps `playing` true and re-emits stale amplitude frames
- **File:** `src-tauri/src/audio/playback.rs`  (lines 336-342)
- **Scope/Category:** audio-tts / bad-assumption   **Confidence:** high
- **Problem:** `SetPaused(true)` calls `sink.pause()` but does not change `sink.empty()`/`len()`, so `now_speaking = !sink.empty()` stays true and `playing` stays true. The amplitude streamer (streaming.rs) gates only on `is_playing()`, so while paused it keeps reading `recent_samples()` and emitting the same stale tail at 60Hz; the avatar/visualizer keeps animating to frozen audio.
- **Why it triggers:** During a paused selection read the avatar lip-syncs to the last buffered samples even though no audio is playing. Not a crash and arguably cosmetic, but it contradicts the design goal of the ring/`is_playing` gate (avoid lip-syncing to non-playing audio). The ring is not cleared on pause and no new samples arrive, so the same window is replayed every tick.
- **Suggested fix:** Track a separate `paused` flag and have the streamer skip emit while paused (or clear/freeze the amplitude output on pause), so the avatar does not animate to stale samples during a pause.

## 9. [LOW] Escape always triggers stop-all-TTS side effect even when no TTS is playing and focus is in terminal
- **File:** `src/lib/shortcuts/dispatcher.ts`  (lines 126-139)
- **Scope/Category:** frontend-settings-status / edge-case   **Confidence:** high
- **Problem:** On every Escape keydown (when no selection-read is active) the handler unconditionally calls `fn()` (stop_tts) as a side effect before letting Escape propagate, regardless of whether any TTS is in flight.
- **Why it triggers:** This is documented as intentional, but it means the stop_tts handler runs on literally every Escape the user presses inside Claude/terminal. If that handler is not cheap/idempotent (it currently is), or later grows to emit IPC/log on each call, this becomes a per-keystroke cost on a very hot key. Worth noting as a bad-assumption that stop_tts is always free to call.
- **Suggested fix:** Gate the side-effect call on an `active`-style check (is anything actually speaking) so Escape only invokes stop when there is TTS to stop; keep pass-through otherwise.

## 10. [LOW] Custom palette merge leaks arbitrary keys from on-disk `custom` into xterm ITheme
- **File:** `src/lib/themes/resolve.ts`  (lines 37-39)
- **Scope/Category:** frontend-settings-status / bad-assumption   **Confidence:** high
- **Problem:** themeFromSetting spreads `t.custom` (a `ThemeColorsWire` = Record<string,string> from disk/IPC) directly over the default palette with no key validation: `{ ...defaultPalette(), ...t.custom }`.
- **Why it triggers:** `custom` originates from settings.json (hand-editable) and the wire type is an open string map. Extra/misspelled keys (or non-color string values) flow straight into the object handed to xterm.js as an ITheme. Most extras are ignored by xterm, but a malformed value on a real key (non-hex string) is passed through unchecked and can produce a broken/garbled terminal palette with no fallback for that channel.
- **Suggested fix:** Project `t.custom` through REQUIRED_THEME_KEYS (pick only known keys, validate `#RRGGBB`) before merging, falling back to the default for any invalid/missing channel.

## 11. [LOW] Usage 'not logged in' result is treated as a transport failure and backs off exponentially
- **File:** `src/lib/status/UsageMeter.svelte`  (lines 76-90)
- **Scope/Category:** frontend-settings-status / bad-assumption   **Confidence:** high
- **Problem:** The poll loop branches on `result && result.snapshot` (success) and `result && result.rate_limited` (429); a structured UsageResult with `snapshot: null, rate_limited: false` (the documented 'unavailable / not logged in' case) falls into the final `else`, increments `failures`, and applies exponential backoff up to MAX_BACKOFF_MS (5 min) exactly like a thrown transport error.
- **Why it triggers:** A logged-out user who then logs into Claude may wait up to ~5 minutes before the widget appears, because a clean 'no data' answer is conflated with a network/IPC error for backoff purposes. The two are semantically different (one is a stable steady-state, the other transient), yet both ramp the same failure counter.
- **Suggested fix:** Distinguish `result === null` (transport error → backoff) from `result` present with empty snapshot (logged-out steady state → poll at a fixed, non-escalating cadence).

## 12. [LOW] startAnim leaves the previous frame timer running across the async loadAnim await
- **File:** `src/lib/spritePlayer.ts`  (lines 200-216)
- **Scope/Category:** frontend-terminals / race   **Confidence:** high
- **Problem:** startAnim bumps gen and awaits loadAnim() without first clearing the currently-scheduled frameTimer (set by the previous animation's showFrame at line 313). During the await, that pending timer can fire advanceFrame(), which reads the still-current curAnim, advances its frame, and reschedules another timer. Only when the new showFrame runs (line 215) is the timer finally clobbered.
- **Why it triggers:** On a state switch or rotation where loadAnim is slow (uncached frames being decoded), the OLD animation keeps ticking and may paint one or more extra frames of the outgoing animation before the new one lands. Cosmetic, but it contradicts the gen-guard's intent of cleanly switching animations.
- **Suggested fix:** Call clearTimeout(this.frameTimer)/this.frameTimer=null at the top of startAnim before the await, so the outgoing animation stops ticking immediately.

## 13. [LOW] Rebind-fallback in attemptSpawn uses pre-await rows/cols captured before fit
- **File:** `src/lib/terminals.ts`  (lines 247-269)
- **Scope/Category:** frontend-terminals / bad-assumption   **Confidence:** medium
- **Problem:** attemptSpawn captures {rows, cols} from entry.term once at line 247, then on the rebind path calls ptyRebindChannel and, on failure, ptyStart(entry.tabId, channel, rows, cols) with those same values. For a renderer-flip recreate the new Terminal is constructed at the previous geometry and only fit later on attach, so rows/cols here are the pre-fit geometry. The fallback pty_start therefore spawns the shell at the snapshot geometry rather than the slot's real size; the SIGWINCH only catches up on the next ResizeObserver/attach fit.
- **Why it triggers:** Edge case (rebind must fail first), and the later fit corrects it, but a shell that renders a full-screen TUI on first paint can briefly draw at the wrong column count.
- **Suggested fix:** Re-read entry.term rows/cols immediately before the fallback ptyStart, or fit before spawning when the host is already attached.

## 14. [LOW] composeContent transcription append can join words without separator after manual edits
- **File:** `src/lib/stt.ts`  (lines 50-55)
- **Scope/Category:** frontend-terminals / edge-case   **Confidence:** medium
- **Problem:** On stt-transcription the code appends with a single space only when cur is non-empty: `cur ? cur + ' ' + text : text`. It assumes cur has no trailing whitespace and text has no leading whitespace beyond the .trim() applied to text. cur is whatever is in composeContent, which may already end in a newline or space (user typed, or a prior transcription). The result can produce double spaces, or if cur ends without space and the intent was a new line, the dictation is glued onto the previous line. Conversely if the user cleared text to whitespace-only, cur is truthy (' ') and you get ' ' + text.
- **Why it triggers:** Minor UX defect: the join logic assumes a clean single-space boundary that the live, user-editable compose buffer does not guarantee. Whitespace-only cur is treated as non-empty.
- **Suggested fix:** Trim cur (or test cur.trim()) before deciding the separator, and collapse to a single space: `const base = cur.trim(); composeContent.set(base ? base + ' ' + text : text)` (preserving intentional content as appropriate).

## 15. [LOW] pty_write drops a brand-new tab's keystroke if TabAdded hasn't been drained yet
- **File:** `src-tauri/src/ipc/commands.rs`  (lines 204-230)
- **Scope/Category:** ipc / race   **Confidence:** medium
- **Problem:** pty_write resolves the per-tab length counter from state.input_lengths with `.ok_or_else(|| ... unknown tab)?`. If the entry is absent the command returns Err and never reaches `registry.write(tab, input)` at line 230 — the keystroke is silently lost. input_lengths is only populated by the state manager when it drains the StateSignal::TabAdded that create_shell_tab/create_ai_tab/open_tool_tab enqueue (state/manager.rs:549). There is no happens-before guarantee that the manager task has processed TabAdded before the frontend mounts the new tab and issues pty_start + pty_write.
- **Why it triggers:** After create_shell_tab returns, the frontend mounts and immediately calls pty_start then pty_write on the new tab. If the single-consumer state-signal task hasn't yet drained TabAdded (e.g. it's mid-tick or under load), input_lengths has no entry for the tab, so the first keystrokes return an error and the bytes never reach the PTY. Symptom: the very first characters typed into a just-created tab can be dropped.
- **Suggested fix:** Treat a missing length counter as non-fatal: fall back to a throwaway AtomicI32 (or lazily insert one) and still perform registry.write, instead of `?`-returning before the write. The counter is only an idle-Listening heuristic and must not gate input delivery.

## 16. [LOW] pty_start holds the tabs async mutex across blocking scrollback file read and PTY spawn
- **File:** `src-tauri/src/ipc/commands.rs`  (lines 44-79)
- **Scope/Category:** ipc / edge-case   **Confidence:** high
- **Problem:** pty_start acquires `state.tabs.lock().await` at line 44 and holds it across `start_tab(...).await` (spawns the PTY) AND across `crate::pty::scrollback::read(&tab)` at line 70, which is a synchronous `fs::read` of the entire persisted scrollback file (scrollback.rs:114), plus seed_scrollback/consume_after_read — all while the single TokioMutex protecting the whole tab registry is held.
- **Why it triggers:** Every other registry-touching command (pty_write, pty_resize, tab_activate, list_tabs, close_tab, etc.) blocks on the same TokioMutex. A slow disk / network drive / antivirus scan during the synchronous fs::read stalls all of them for the duration. The scrollback read needs no registry lock at all — it only needs `&tab`. Holding the lock across it serializes unrelated IPC behind disk latency.
- **Suggested fix:** Read the scrollback file BEFORE taking the registry lock (or after dropping it), and only re-acquire the lock for seed_scrollback. The read takes only `&tab` and doesn't touch the registry.

## 17. [LOW] create_shell_tab / create_ai_tab / open_tool_tab leave an orphan tab if the TabAdded send fails
- **File:** `src-tauri/src/ipc/tab_lifecycle.rs`  (lines 221-239)
- **Scope/Category:** ipc / resource-leak   **Confidence:** medium
- **Problem:** The creation commands commit the settings entry (state.settings.set, line 221) and the registry entry (insert_user_tab, line 226) BEFORE sending StateSignal::TabAdded (line 229). If the send fails the command returns Internal error, but the persisted settings entry and the registry entry (with its spawned PtyManager) are already committed and are never rolled back.
- **Why it triggers:** On a state-signal channel-closed error the user sees a failure toast, yet a phantom tab now exists in settings and in the registry with no frontend representation (no TabCreated emitted). On next launch the orphan settings entry materializes a tab the user never confirmed. Same pattern in create_ai_tab (319/328) and open_tool_tab (844/852).
- **Suggested fix:** On TabAdded send failure, roll back: remove the registry entry and the settings tab entry before returning the error, or send the signal first and only persist after it succeeds.

## 18. [LOW] set_active_tab persists active_tab_id with an unserialized read-modify-write that can be clobbered
- **File:** `src-tauri/src/ipc/commands.rs`  (lines 606-610)
- **Scope/Category:** ipc / race   **Confidence:** high
- **Problem:** After activating the tab, set_active_tab does `let mut snap = state.settings.current(); snap.session.active_tab_id = ...; state.settings.set(snap);` outside the registry lock and without the lifecycle_serializer.

## 19. [LOW] Offload loopback/host/health only start when offload is enabled AT LAUNCH; enabling it later from Settings never starts the loopback discovery endpoint
- **File:** `src-tauri/src/main.rs`  (lines 378-405)
- **Scope/Category:** main-misc / bad-assumption   **Confidence:** high
- **Problem:** In the Tauri setup hook, the warm host, health watch, metrics poller, and the loopback endpoint (which writes the discovery file MCP children read to connect back) are spawned only inside `if snap.enabled { ... }`, evaluated once from the settings snapshot taken at launch (line 378). The OffloadService and OffloadSupervisor are managed unconditionally, and `OffloadService::offload` lazily warms the host on first call, but nothing re-runs `Loopback::start` / `spawn_health_watch` / `spawn_metrics_poller` if the user toggles offload on later via Settings.
- **Why it triggers:** A user who launches with offload disabled, then enables it in Settings during the same session, gets a service that can lazily route an offload internally but never has the loopback discovery endpoint running. External Claude-Code MCP children that rely on the loopback discovery file to connect back will not find it until the app is restarted. The behavior is silently different depending on whether offload was enabled at launch vs. mid-session.
- **Suggested fix:** Add a settings-change watcher (subscribe to SettingsHandle in main or inside OffloadService::new) that, on an enabled false→true transition, runs the same warm_host/spawn_health_watch/spawn_metrics_poller/Loopback::start sequence (and tears it down on true→false). Alternatively document that enabling offload requires a relaunch.

## 20. [LOW] content::run_cleanup removes the wrong (today's) cached writer based on an old file's name prefix
- **File:** `src-tauri/src/content.rs`  (lines 176-182)
- **Scope/Category:** main-misc / edge-case   **Confidence:** high
- **Problem:** When deleting an aged-out rolled file like `claude.log.2026-05-08`, the code computes `prefix = name.split(".log.").next()` = `claude` and removes `writers["claude"]` from the cache. But the cached writer keyed `claude` is the appender for TODAY's file, not the old dated file being deleted. The old file is not held open by that writer (tracing-appender only holds the current day's handle), so dropping the live writer is both unnecessary and forces an avoidable reopen on the next PTY burst.
- **Why it triggers:** Not a correctness bug in deletion, but it needlessly drops and recreates the active writer for a tab whenever any of that tab's historical files age out — a small hot-path hiccup, and it can drop buffered state on the active appender. The Windows-handle rationale in the comment only applies to today's file, which is never the one being deleted here (fresh mtime).
- **Suggested fix:** Only drop the cached writer if the file being deleted is actually today's current file (or just don't drop it at all for aged files — the open handle is never on the old dated file).

## 21. [LOW] Tasks mentioning git/diff/commit require an MCP `git` server and get NoToolMatch on a scoped local backend that lacks it
- **File:** `src-tauri/src/offload/router.rs`  (lines 274-278)
- **Scope/Category:** offload-core / bad-assumption   **Confidence:** medium
- **Problem:** analyze_task pushes the required tool "git" whenever the text contains "git ", "commit", "blame", or "diff". `git` is an MCP *server* name (LOCAL_DATA_TOOLS lists it alongside the native tools), not a native tool. A local/LAN backend configured with ToolScope::Only{["read_file","code_search","run_command"]} (no git MCP server connected) will fail allows_all(["read_file","git"]) and select() returns NoToolMatch.
- **Why it triggers:** A perfectly serviceable local backend with run_command (which can shell out to `git`) is refused for any task whose description merely mentions a diff or a commit, because the router demands a dedicated `git` MCP server that may not be configured at all. The user sees 'no ready backend allows them' for a task the backend could actually do via run_command. The same over-restriction hits 'command'/'build'/'unit test' → required "run_command", but at least that is a real native tool.
- **Suggested fix:** Only require the `git` (and other MCP-server) tool when that server is actually present in the advertised tool set / configured mcp_servers; otherwise fall back to run_command, or drop git from the hard-required set and treat it as a soft preference.

## 22. [LOW] global_in_flight can transiently under-report (and the shrink forget-loop can over-reclaim) during cap reconciliation
- **File:** `src-tauri/src/offload/service.rs`  (lines 186-220)
- **Scope/Category:** offload-core / race   **Confidence:** high
- **Problem:** reconcile_global_cap stores the new (smaller) target into global_cap immediately, then spawns a task that drains `current-target` permits asynchronously. global_in_flight() computes `global_cap - available_permits`. Between the store and the drain completing, available_permits still reflects the old larger pool, so `global_cap (small) - available_permits (large)` saturates to 0, masking real in-flight loads. Conversely, if the cap is grown again (by config change) while the shrink-drain task is still acquiring, the drain forgets permits that the grow just added, double-counting the shrink.
- **Why it triggers:** The atomic global_cap and the semaphore permit count are updated non-atomically with respect to each other and an async drain, so the derived in-flight figure (shown in Settings and logged at routing) is briefly wrong, and concurrent grow+shrink reconciles can leave the gate sized inconsistently with global_cap.
- **Suggested fix:** Serialize cap reconciliation under a mutex and only update global_cap after the permit add/forget completes; for shrink, store the target after the drain loop finishes rather than before it starts.

## 23. [LOW] After a llama-server restart with smaller -np, RemoteBackend.in_flight can report a too-high busy count
- **File:** `src-tauri/src/offload/remote.rs`  (lines 213-244, 295-304)
- **Scope/Category:** offload-core / edge-case   **Confidence:** high
- **Problem:** note_total_slots deliberately never shrinks slots/gate. If a remote llama-server is restarted with a smaller -np (e.g. 4 -> 1), refresh_props sees total_slots=1 but leaves self.slots at 4 and the gate at 4 permits. slots() returns 4 and in_flight() = 4 - available_permits.
