# Milestone V9-01: Per-Project Code Knowledge Graph (code + docs, agent-queryable)

> **Release tag:** TBD by the user at ship time (V-series numbering is independent of the git tag, per the V6-01 convention). The "V9-01" label is a placeholder and opens a new feature pillar — *code intelligence* — distinct from the audio pillars (V6 STT, V7 voice cloning) and the compute-offload pillar (V8). Adjust the number freely at ship time.
>
> **On the name.** The user described this as a "Graph DAG." A code knowledge graph is **not** a DAG — call graphs, import cycles, and mutual recursion are genuinely cyclic — so this doc calls it a **code knowledge graph** (CKG). The chosen storage/query engine (CozoDB, Datalog) handles cycles natively via recursive rules, which is one reason it fits.
>
> **No separate spike.** Following the V8 convention, the stack's unknowns are validated **inline during implementation** and flagged where they bite (see Risks). The one genuinely new dependency surface — embedding the parse→graph pipeline and an in-process graph DB in the portable binary — is the thing to prove out early (binary-size + index-latency on a real repo).
>
> **Motivation.** Both consumers of cImp's tool surface — the cloud Opus session *and* the local offload worker (V8) — currently rediscover a project's structure from scratch every task: `grep` for a symbol, read a file, follow an import, read another file. That is exactly the token-heavy churn V8 set out to reduce, but V8 only *moves* the churn to a local model; it doesn't make the structure **cheap to query**. A persistent, per-project graph of symbols / calls / imports / docs turns "find every caller of `foo` and where it's documented" from a dozen file reads into one indexed query — for *both* Opus (over MCP) and the offload agent (as a native tool).

## Purpose

Add a **per-project code knowledge graph** to cImp: an on-disk graph of the project's code (files, symbols, definitions, references, calls, imports) and its documentation (markdown + doc-comments, chunked and linked to the symbols they describe), built and maintained **inside the cImp Rust binary**, stored **in the project folder** so it loads automatically whenever cImp launches a tab in that folder.

The graph is exposed to **two consumers** through the surfaces V8 already established:

1. **The cloud Opus session** — graph query tools (`graph_find_symbol`, `graph_callers`, `graph_search_docs`, …) added to the **MCP server cImp already injects into Claude tabs** (`--mcp-config`, V8-01 Phase D). Opus queries the graph directly to navigate the codebase without burning context on `grep`/read round-trips.
2. **The local offload worker** — the same queries exposed as **native offload tools** (alongside `code_search`/`read_file`, V8-01 Phase B), so an `offload_task` can resolve symbols and call chains structurally instead of grepping.

Everything stays **local and offline** — parsing, graph construction, and querying are pure Rust in cImp's binary, consistent with the [[project_constraints]] single-binary / no-Python preference. The graph DB is an **embedded, in-process** store (no server daemon), its data a single file under the project's `.cimp/` directory.

### Why per-project (a deliberate exception to global-only)

App-wide services (avatar, TTS voice, the offload `llama-server`) are intentionally **global-only** ([[project_global_only_avatar_tts]]) — one shared instance for the whole app. The code graph is the opposite by nature: it *is* the project. The user's framing — "stored in the project folder so it is automatically loaded when cImp is started in the project folder" — is the whole point. So this milestone introduces cImp's first **per-project, on-disk, auto-discovered** artifact, keyed by the launch cwd of each tab. The global-only posture for shared *services* is unchanged; this is project *data*, which lives with the project.

### How it fits the existing architecture (heavy reuse of V8)

This milestone is **additive on top of V8-03's warm-service + loopback design** — it adds a second app-owned service alongside the offload service and exposes it through the *same* two consumer paths, rather than inventing new plumbing:

- **The Tauri app owns the graph.** A new `graph::GraphService` lives in `AppState` beside the offload service. It manages one `GraphIndex` per open project root (open/build the `.cimp/graph.db`, run the file watcher, answer queries). One in-process store per project, shared by every consumer.
- **Toward Claude, reuse the V8 MCP bridge.** The `cimp --offload-mcp` child (which Claude spawns with `cwd` = the project root) gains `graph_*` tools. It resolves the project root from its cwd and **proxies queries to the app over the existing V8-03 loopback endpoint** (`POST /graph/query`), exactly as it proxies `offload_task` to `POST /run`. When the app isn't running it can open the project's `graph.db` read-only itself (self-contained fallback, same pattern as offload). Session-scoped injection only — `~/.claude` is never written ([[project_statusline_context_bar]]).
- **Toward the offload worker, reuse the native-tool seam.** `offload/agent.rs`'s tool router gains `graph_*` native tools that call `GraphService` in-process (the offload service and graph service are both app-owned, so this is a direct call, no loopback).
- **Settings** add an additive `GraphSettings` block with the established `#[serde(default)]` discipline (mirrors `OffloadSettings`).
- **Status** surfaces per-project index state (building / ready / stale, node+edge counts, last-updated) in the bottom-bar conventions and a Settings readout, consistent with the V8 status surfacing.

## Architecture

```
  cImp (Tauri app, long-lived)
    └─ graph::GraphService  (held in AppState, beside the V8 OffloadService)
         ├─ per project root:  GraphIndex
         │     ├─ store:   <project>/.cimp/graph.db   (CozoDB, SQLite backend — one file)
         │     ├─ builder: tree-sitter parse  →  symbols/refs/calls/imports/doc-chunks
         │     │            (incremental; precise name-binding via stack-graphs where available)
         │     └─ watcher: notify(fs) → debounce → re-index only changed files
         └─ query API:  find_symbol · references · callers/callees · imports · transitive(dir,depth) ·
                        outline · neighborhood · search_docs · struct_search(ast-grep) · semantic_search
                  ▲                                         ▲
   (native, in-proc) │                                       │ (loopback HTTP, V8-03 channel)
                  │                                         │  POST /graph/query  { project, op, args }
  V8 offload::agent │                                         │
    native tools:   │                          cimp --offload-mcp  (per Claude session)
    graph_find_symbol, …                          tools: graph_find_symbol, graph_callers,
                                                          graph_search_docs, graph_outline, …
                                                  ├─ resolves project root from its cwd
                                                  ├─ app up   → proxy to /graph/query  (warm index)
                                                  └─ app down → open graph.db read-only (fallback)
                                                          │
                                                          ▼
                                                  Claude Code (Opus)  ── queries the graph directly
```

- **One graph per project root, owned by the app.** Keyed by canonicalized launch cwd. Built once (first open), then kept fresh by an fs watcher. Both consumers read the *same* warm index — no per-call rebuild.
- **The two consumer paths mirror V8 exactly.** Opus reaches the graph through the MCP child → loopback (warm) or the child's own read-only open (fallback). The offload agent reaches it in-process. The graph DB file on disk is the shared source of truth in both layouts.
- **Build is incremental and local.** tree-sitter parses each file; a `tags.scm`-style query (ctags convention, shipped by most grammars) yields definitions + references; import/call edges come from the same parse. Precise cross-file name resolution uses **stack-graphs** for languages with `tsg` rules; everything else gets the broadly-available tag-based resolution. No external indexer process, no Python, no JVM.
- **Semantic search (Phase G) adds an embedding backend.** The indexer embeds doc/code chunks via an OpenAI-compatible `/v1/embeddings` endpoint — the user's plan is to **repurpose the V8 "fast" remote offload box (an RTX 3070, 8 GB)** to serve an embedding model — and stores the vectors in CozoDB's HNSW index; `graph_semantic_*` embeds the query and runs ANN search. Full-text remains the fallback whenever the embedding backend is down, so the structural graph never depends on it.
- **A reserved "Code Graph" monitor tab (Phase I)** renders the live operational view — DB/index status, embedded-vs-current freshness, indexing/embedding queues, active queries, embedder health, and an activity log — from a throttled `GraphEvents` stream. It mirrors V8's Offload Server tab for reserved/non-closable/feature-gated behavior, but is **app-rendered** (the first non-PTY tab), since the indexer/embedder/watcher run *inside* the app and have no stdout to mirror.

## Engine choices (decided, from research)

Two layers — **extraction** (code → graph) and **storage/query** (hold + answer) — chosen for pure-Rust embeddability in a portable single binary with no Python/JVM sidecar. (Full survey in the V9-01 research notes; summary of the verdict below.)

### Storage + query: **CozoDB** (SQLite backend)

```toml
# Cargo.toml
cozo = { version = "0.7", features = ["storage-sqlite"] }
```

- **100% Rust-native, truly embedded** (in-process, like SQLite) — no daemon. The SQLite backend gives a **single `graph.db` file** in `.cimp/`, exactly matching "stored in the project folder."
- **Datalog is ideal for a code graph.** Recursive queries — transitive callers, dependency closure, reachability — are two-line rules, not the painful recursive CTEs they'd be in SQL or the awkward variable-length paths in Cypher. Built-in graph algorithms (PageRank, connected components, shortest path) come free for ranking/"most central symbol" features.
- **MVCC + ACID** makes concurrent reads (two Claude tabs + the offload worker) safe while the watcher writes incremental updates.
- **Built-in HNSW vector + full-text search** — full-text covers doc/symbol search at MVP; the same store's vector index is what Phase G's semantic search uses, so no second store is ever added.
- **License: MPL-2.0** — file-level copyleft. Using `cozo` unmodified as a Cargo dependency triggers **no copyleft on cImp's own code**; obligations are attribution + a source pointer in the third-party-licenses file. Strictly milder than the GPLv3 espeak-ng already shipped ([[project_phonemizer_choice]]). *(Considered and rejected: KuzuDB — excellent Cypher engine but its repo was archived Oct 2025; SurrealDB — BSL-1.1 is not OSI-approved; Oxigraph — SPARQL/RDF model is an awkward fit for a property graph; petgraph — in-memory only, no persistence.)*

### Extraction: **tree-sitter** (+ `tags.scm`), **stack-graphs** where available, **ast-grep** for structural search

```toml
tree-sitter = "0.24"
tree-sitter-rust = "..."     # + ts grammars per supported language
# stack-graphs + tree-sitter-stack-graphs — optional precision layer (supported langs)
ast-grep-core = "..."        # structural AST-pattern search → graph_struct_search
```

- **tree-sitter** (MIT, C core + first-class Rust bindings) parses every supported language fast and incrementally. The **`tags.scm` query** convention (the ctags/code-navigation query many grammars ship) yields definitions and references across a broad language set with no per-language Rust code — the MVP symbol/reference layer.
- **stack-graphs** + `tree-sitter-stack-graphs` (MIT/Apache-2.0, **pure Rust**) provide *precise* cross-file name binding (def↔ref resolution through scopes/imports) for languages with `tsg` rules (Python, JS, TS, Java). Used as a **precision upgrade** where rules exist; tag-based resolution is the fallback elsewhere. **Caveat:** the stack-graphs repo was **archived by GitHub (Sep 2025)** — stable and usable, but we pin a frozen version and may fork. Because it's an *optional* precision layer behind the always-available tag layer, the archive risk is contained.
- **ast-grep** (`ast-grep-core`, MIT, pure Rust) is **included** as the **structural-pattern-search** engine — it runs tree-sitter AST patterns (e.g. "every `.unwrap()`", "functions shaped like *X*", "calls to `foo` with a literal first arg") that neither symbol lookup nor semantic similarity can express, surfaced as the `graph_struct_search` tool. It reuses the same tree-sitter parses, so it's a thin, pure-Rust add. *(It complements — doesn't replace — the symbol/ref graph: structure-by-shape vs. structure-by-name.)*

> **Reality check:** none of these is the *graph* — they're the parse/resolve front end. The node/edge schema, incremental update logic, and Datalog query layer are cImp code on top of CozoDB. This is a "compose pure-Rust building blocks," not "adopt a turnkey product," milestone — deliberately, because every turnkey code-graph-with-MCP (Serena, blarify, Potpie, code-graph-rag) is a Python service that violates the no-sidecar constraint, and the heavyweight engines (Joern, Kythe, Glean) need a JVM or server daemon.

## Decisions locked (from discussion)

- **Per-project, on-disk, auto-discovered.** The graph for a project lives at `<project>/.cimp/graph.db` and is opened/built when cImp launches a tab whose cwd is (or is within) that project root. No global graph, no central registry — the artifact travels with the project. *(First per-project on-disk artifact in cImp; the global-only posture for shared services is unchanged — [[project_global_only_avatar_tts]].)*
- **Storage = CozoDB, SQLite backend; extraction = tree-sitter (+ stack-graphs where available) + ast-grep for structural search.** Pure Rust, embedded, single file, no sidecar. (Engine section above.)
- **`.cimp/` is the per-project home; recommend git-ignoring it.** The graph is a derived cache (rebuildable from source), so the README/docs recommend adding `.cimp/` to `.gitignore`. cImp can offer to append it on first build. The DB is *not* committed — it's machine/version-specific and would churn. *(A future "share a prebuilt graph" feature could opt back in, but not here.)*
- **Two query surfaces, both reusing V8 plumbing.** MCP tools toward Claude (added to the existing `--offload-mcp` server, proxied over the V8-03 loopback to the warm app-side index, with a read-only direct-open fallback when the app is down) **and** native tools toward the offload agent (in-process call to `GraphService`). No new injection mechanism, no new IPC channel — both already exist from V8.
- **Build is lazy + incremental, never blocks launch.** Opening a project does not synchronously index it. The first index runs in the background (status: *building*); queries before it's ready return a clear "index building, N% / M files" result rather than blocking or erroring. After the initial build, an fs watcher (`notify`) re-indexes **only changed files** (debounced), so steady-state cost is per-edit, not per-repo. Mirrors the STT/TTS lazy-engine fail-soft pattern.
- **Read-only to consumers; writes only from the builder.** Opus and the offload worker can only *query* the graph; they never mutate it. The single writer is the app's indexer (initial build + watcher). This keeps the read-class safety posture identical to V8 (the offload worker stays read-only) and avoids concurrent-writer complexity.
- **Documentation is a first-class node type, linked to code.** Markdown files and doc-comments (`///`, `/** */`, docstrings — extracted by tree-sitter) are chunked and stored as `doc_chunk` nodes with `documents` edges to the symbols/files they describe (by proximity and by explicit reference where resolvable). `graph_search_docs` searches them (full-text at MVP). This is what lets "where is X documented, and what does the doc say" be one query.
- **Capabilities reported dynamically, like V8.** The `graph_*` tools are advertised to Opus only when a graph exists / is enabled for the current project, and the per-project index state (building/ready/stale + counts) feeds the same `tools/list_changed` mechanism V8 uses, so Opus knows whether the graph is queryable *now*.
- **Languages ship incrementally.** MVP targets the languages cImp itself and its users live in: **Rust, TypeScript/JavaScript, Python, Markdown** (docs). The grammar set is a `Cargo.toml` list; adding a language is adding a grammar + its `tags.scm` (+ optional `tsg`). Unsupported files are skipped (logged), never fatal.
- **Opt-in, default off — but cheap to turn on.** `graph.enabled` defaults **false** (a fresh install shouldn't silently index every project the user opens). When enabled, indexing is per-project and lazy. Unlike the ~20 GB offload server, the footprint is small (a few MB of DB for a mid-size repo), so the barrier is low; a first-run prompt can offer to enable it.
- **Bounded index size + ignore rules.** The indexer honors `.gitignore` + a configurable `graph.ignore` list (default: `node_modules`, `target`, `.git`, `dist`, build dirs, vendored/minified files, files over a size cap). Generated/minified files pollute a code graph and bloat the DB, so they're excluded by default and the exclusions are visible/editable.
- **Semantic search ships in this milestone (Phase G), served by a dedicated embedding backend.** It's layered *after* the structural graph + full-text MVP and gated by `semantic_search` (default off), but it is **committed, not deferred**. The structural core (symbols/calls/imports/full-text) still needs no embedding model at all and runs with the embedding backend absent. Embeddings come from a **remote OpenAI-compatible `/v1/embeddings` endpoint**; the user's plan is to **repurpose the V8 "fast" remote offload backend — the RTX 3070, 8 GB box — to serve an embedding model** (e.g. `nomic-embed-text-v1.5` / `bge-large-en-v1.5` / `mxbai-embed-large` as a GGUF under `llama-server --embedding`; all well under 2 GB, so 8 GB is ample). **Tradeoff (the user's call):** an embedding model can't also serve fast *chat*, so dedicating that GPU removes the V8 "fast" offload chat tier — fast-tier tasks then route to the quality backend, or a tiny chat model co-resides in the spare VRAM. The DB records `{embedding_model, embedding_dims}`; changing the model requires a re-embed + HNSW rebuild (dimensions can't be mixed).
- **Semantic search needs a live embedder at *both* index time and query time — otherwise it degrades to full-text.** A query must be embedded into the *same* vector space as the chunks, so **stored vectors are unusable without a reachable embedder** (you can't embed the question). Therefore: the `graph_semantic_*` tools are **advertised health-accurately** (V8-style) — offered only when an embedding endpoint is reachable; when it is **unconfigured, removed, or down**, the tools transparently run **full-text and say so in the result** rather than erroring or returning nothing. The structural graph + full-text search need **no embedder, ever**, and are unaffected. *(So the default state — `semantic_search` off, no endpoint — is a fully working graph, just without semantic ranking.)*
- **Embedding is opportunistic + back-filled; an "embedding epoch" governs validity (handles stale/old data).** Chunks are **always stored** with their structural + full-text data regardless of whether an embedder exists; embedding is a **separate opportunistic pass** that runs whenever a reachable endpoint is present — embedding the **backlog** of unembedded chunks (first-time configuration, or recovery after downtime) and re-embedding content-changed chunks (by hash). Every vector is tagged with an **embedding epoch = {model id, dimensions, embed-schema version}**. Semantic queries run **only against current-epoch vectors**; changing the model **bumps the epoch**, marks prior vectors superseded, and kicks a background re-embed — until coverage is adequate the tools report **partial coverage** or fall back to full-text. The DB **never mixes epochs/dimensions in one ANN search**, so a half-migrated or mixed-model index can't silently return garbage. Superseded vectors are kept (not deleted) so re-pointing at the *same* model/dim is instantly usable again with no re-embed.
- **A reserved, read-only "Code Graph" monitor tab — the live operational view.** Mirroring V8's Offload Server tab (reserved system tab, **non-closable**, materialized iff `graph.enabled` via the integrity check, removed when disabled), with one architectural difference: it is **app-rendered, not PTY-backed** — the indexer/embedder/watcher/query layers run inside the app, not as a child process, so there's no stdout to mirror. It is cImp's **first non-terminal tab**: the frontend tab host branches on `TabKind::GraphMonitor` to mount a live Svelte dashboard instead of xterm. One **global** tab with a collapsible **section per open project root** (the focused root expanded), fed by the throttled `GraphEvents` stream. Observational by design (the single writer stays the indexer); the Rebuild / Pause-watcher / Rebuild-embeddings actions from Settings are mirrored as a small action row for convenience.
- **One `GraphEvents` bus is the single source of truth for the monitor, the bottom-bar affordance, and the Settings readout.** The builder, watcher, embedder, and query layers emit events (file indexed, watcher backlog changed, embed batch started/finished, query started/finished, epoch bumped, embedder health changed) into one in-app bus. To avoid flooding the UI during a full build (thousands of files), the service pushes a **throttled snapshot** (~2–4 Hz: counters, queue depths, in-flight lists, coverage/epoch/health) plus a **bounded, coalesced recent-activity ring** (e.g. "indexed 312 files (+45)") — never one IPC message per file. So the tab, bottom bar, and Settings can never disagree.
- **Session-scoped injection.** Like the status line and V8's offload MCP config, the `graph_*` MCP tools are injected only into cImp-launched Claude tabs; `~/.claude` is never written ([[project_statusline_context_bar]]).

## What This Milestone Delivers

Phases get **one real graph query answering from a real index** as early as possible, then layer on incremental updates, the second consumer path, docs, settings, and packaging.

**Phase A — Schema + builder (code → CozoDB), one language, full build**

1. `graph/schema.rs` — the CozoDB relation set (Datalog stored relations) and a thin typed wrapper. Core relations:
   - `file {path, lang, hash, mtime}` — indexed files.
   - `symbol {id, name, kind, file, start_line, end_line, signature, doc}` — definitions (fn/struct/trait/class/method/const/module/…).
   - `ref {symbol_name, file, line, col, resolved_id?}` — references (resolved to a `symbol.id` where stack-graphs/tags allow, else name-only).
   - `edge_call {caller_id, callee_id_or_name}`, `edge_import {file, module, imported_name}`, `edge_contains {parent_id, child_id}`.
   - `doc_chunk {id, source_path, anchor, text}`, `edge_documents {doc_id, symbol_id_or_file}`.
   - Indices on `symbol.name`, `ref.symbol_name`, and the edge keys; a full-text index on `symbol.doc` + `doc_chunk.text`.
2. `graph/builder.rs` — `index_file(path)`: tree-sitter parse → run the language's `tags.scm` → emit `symbol`/`ref` rows; walk the tree for call/import/contains edges; extract doc-comments → `doc_chunk` + `edge_documents`. Idempotent per file (delete-then-insert by `file.path`). Start with **Rust** (the codebase itself) for a tight feedback loop.
3. `graph/index.rs` — `GraphIndex`: open/create `<root>/.cimp/graph.db`, run a **full build** (walk the tree honoring ignore rules, `index_file` each), record schema/version metadata. Expose `is_ready()`, `stats()` (node/edge counts, last build).

**Phase B — Query API + first MCP tool, end-to-end**

4. `graph/query.rs` — the typed query API over CozoDB Datalog: `find_symbol(name)`, `references(name|id)`, `callers(id)`, `callees(id)`, `imports(file|module)`, `transitive(id, dir, depth)` (recursive Datalog), `outline(file)`, `neighborhood(id)` (a small, token-bounded subgraph summary for context), `search_docs(query)` (full-text), and `struct_search(pattern)` (an **ast-grep** structural AST-pattern match over the indexed files — a parse-time match, not a DB query). Every result is **token-bounded** (cap rows + snippet length) with a truncation marker — the same discipline as V8's tool-result caps, since these feed an LLM context.
5. `graph/mcp.rs` (or extend `offload/mcp.rs`) — register `graph_find_symbol`, `graph_references`, `graph_callers`, `graph_callees`, `graph_imports`, `graph_search_docs`, `graph_outline`, `graph_struct_search` as MCP tools in the `cimp --offload-mcp` server. Each resolves the project root from the child's cwd and calls the query API. **End-to-end:** in a real `claude` session, `graph_find_symbol("build_pre_args")` returns its definition site + signature + doc, and `graph_callers` returns its call sites — from the index, with zero `grep`.

**Phase C — App-owned service + warm index + loopback proxy (reuse V8-03)**

6. `graph/service.rs` — `GraphService`, app-owned (in `AppState`), holds a map of `project_root → GraphIndex`, opens/builds lazily on first request for a root, and serves queries from the **warm** in-memory-cached CozoDB handle (no per-call open).
7. Extend the **V8-03 loopback endpoint** with `POST /graph/query { project, op, args }` (token-authed, loopback-only — identical security model). `graph/mcp.rs` becomes proxy-first: **app up → `POST /graph/query`** (warm); **app down → open `graph.db` read-only** in-child (fallback). One shared query core behind both, so they can't drift (the V8-03 proxy/fallback discipline).
8. Wire `GraphService` into the offload agent: `offload/agent.rs`'s tool router gains the same `graph_*` operations as **native offload tools** (in-process call — no loopback), so an `offload_task` resolves symbols/call chains structurally.

**Phase D — Incremental updates (the fs watcher)**

9. `graph/watcher.rs` — per open project, a `notify` watcher (debounced ~300 ms) that maps changed/created/deleted paths to `index_file`/delete, honoring ignore rules. Coalesce bursts (branch switch, save-all). Update `file.hash`/`mtime` and re-index only what changed; surface a transient *re-indexing* status. A periodic **staleness check** (compare `file.mtime`/hash on open) catches edits made while cImp was closed and repairs them in the background.

**Phase E — More languages + docs as first-class**

10. Add **TypeScript/JavaScript, Python** grammars + `tags.scm`, and **stack-graphs `tsg`** for the languages that have it (precise resolution where available; tag-resolution fallback elsewhere). Add **Markdown** parsing → `doc_chunk` nodes; link docs to code by path proximity and by resolvable symbol references in code fences/inline code. `graph_search_docs` now spans markdown + doc-comments.

**Phase F — Settings + status surface**

11. `GraphSettings` surfaced in Settings: **`enabled`** toggle; per-open-project **index status** rows (root, state building/ready/stale, node+edge counts, last-updated, DB size) with **Rebuild** / **Pause-watcher** buttons; a **language toggles** list; an **ignore-rules** editor (defaults shown, `.gitignore` honored); a **doc-indexing** toggle; a **result-cap** group (max rows / snippet length per query); and a **semantic-search** group (`semantic_search` toggle, **embedding-endpoint URL + model** fields, **Test embedding** and **Rebuild embeddings** buttons, the `embed_code_bodies` sub-toggle, and a live readout of **embedder state** (configured / reachable / unconfigured / unreachable), **coverage** (embedded N / M chunks, %), the active **epoch** (model@dims), and **backlog** (chunks awaiting embed/re-embed) — so a "no embedder configured" or "mid-re-embed" state is visible, not silent; *these semantic controls back the Phase-G pipeline and stay inert until it lands*). A "Test query" box runs `find_symbol` against the current project. Status indicators reuse the bottom-bar conventions; a small "graph" affordance shows building/ready per active tab's project.

**Phase G — Semantic search (committed): embedding pipeline + vector index**

12. `graph/embed.rs` — an **embedding client** against an OpenAI-compatible `POST /v1/embeddings` endpoint (reuse `reqwest`; same wire style as the V8 offload client), configured by `embedding_endpoint` + `embedding_model`. Embedding is an **opportunistic, back-filling pass**: every chunk row carries an `embed_epoch` (null = unembedded); whenever the endpoint is reachable, a background worker embeds the **backlog** of null/stale chunks in **batches** and writes vectors tagged with the current epoch `{model id, dims, schema}`. So chunks are stored and structurally/full-text queryable the instant they're indexed, and vectors fill in when (and only when) an embedder exists — first configuration, recovery after downtime, or a model change all converge on the same back-fill path. The DB records the current epoch; a model/dim change **bumps it** (background re-embed) and the indexer **refuses to mix dimensions in one index**. **Deployment (the user's plan):** repurpose the V8 "fast" remote offload box — the **RTX 3070, 8 GB** — to serve an embedding model (e.g. `nomic-embed-text-v1.5`, `bge-large-en-v1.5`, or `mxbai-embed-large` as a GGUF under `llama-server --embedding`); 8 GB is ample (these models are well under 2 GB). *(Tradeoff: an embedding model can't also serve fast chat, so dedicating that GPU drops the "fast" offload chat tier — fast tasks route to the quality backend, or a tiny chat model co-resides in the spare VRAM.)*
13. CozoDB **HNSW vector index** over the current-epoch chunk vectors, plus the tools `graph_semantic_docs(query)` and `graph_semantic_search(query)` (the latter spanning code + docs): embed the query via the same endpoint, run ANN search **scoped to the current epoch**, and return the top-k chunks — token-capped, each carrying its **source symbol/file link** so Opus can jump from a semantic hit straight to the exact location. **Graceful degradation, three cases, all transparent:** (a) **no embedder reachable** (unconfigured / removed / down) — the query can't be embedded, so the tool runs **full-text and labels the result as a keyword fallback**; (b) **embedder up but coverage partial** (back-fill or re-embed in progress) — run ANN over what's embedded and **note the coverage %** so Opus knows the semantic view is incomplete; (c) **fully covered** — normal ANN. The structural graph never depends on the embedding box being up. Capability reporting (V8-style `tools/list_changed`) flips the semantic tools' advertised availability as the embedder's reachability changes.
14. **Incremental re-embed.** The fs watcher re-embeds only the chunks of changed files (delete stale vectors, embed new ones); chunks that couldn't be embedded because the backend was down are **flagged and back-filled** when it recovers. A sub-toggle **`embed_code_bodies`** (default off) extends embedding from docs + signatures to full symbol bodies for semantic *code* search, at the cost of more vectors / a larger index.

## What This Milestone Does NOT Do

- **Bundle precise resolution for every language.** Tag-based (ctags-style) defs/refs are the universal baseline; precise stack-graphs name binding ships only for languages with `tsg` rules. Languages without get name-level resolution (good for navigation, imperfect for overload disambiguation). Closing that gap per-language is a followup.
- **Data-flow / control-flow / taint analysis.** This is a *navigation* graph (symbols, refs, calls, imports, docs), not a full code-property graph. Dataflow/CFG (the Joern/CPG feature set) is explicitly out — it needs a JVM-class engine and a far heavier schema. Possible future pillar, not here.
- **Write/edit through the graph.** The graph is read-only to consumers; no "rename symbol across the repo" or refactoring operations. The single writer is the indexer. Mutation tooling is a deliberate future decision with its own safety design (consistent with the V8 read-only posture).
- **Commit or share the graph.** `.cimp/graph.db` is a local derived cache, git-ignored by recommendation. A "ship a prebuilt graph with the repo" feature is a followup, not this milestone.
- **Cross-project / monorepo-wide federation.** One graph per project root. A graph spanning multiple roots (or querying another project's graph) is out of scope.
- **Replace `code_search`/`read_file`.** The native offload search tools (V8-01) stay — the graph complements them (structure) rather than replacing grep (arbitrary text). Opus/offload pick the right tool per task.
- **Visualize the graph topology.** The Code Graph tab is an **operational** dashboard (status / queues / freshness / activity), **not** a node-link graph explorer — browsing the call/import graph visually stays the "visual graph explorer" followup.
- **On-device / in-process embedding.** Phase G's semantic search uses a **remote** embedding endpoint (OpenAI-compatible `/v1/embeddings`, the repurposed 3070 box). Embedding *in-process* on-device (e.g. a small `bge` model via the `ort` runtime already used for TTS/STT) to drop the remote dependency is a followup. The structural core (symbols/calls/imports/full-text) needs no embeddings at all and runs with the embedding backend absent.

## Test Plan

**Phase A (schema + builder)** — Unit: indexing a fixture Rust file yields the expected `symbol` rows (name/kind/line/signature) and `edge_call`/`edge_import`/`edge_contains` rows; re-indexing the same file is idempotent (no dup rows); a syntactically broken file degrades to partial symbols, never panics; ignore rules skip `target/`. Manual: full-build cImp's own `src-tauri/` and eyeball that key symbols (`build_pre_args`, `OffloadService`) are present with correct files/lines.

**Phase B (query + MCP)** — Unit: `find_symbol`/`callers`/`callees`/`transitive` return correct rows against a known fixture graph; `graph_struct_search` matches a known **ast-grep** AST pattern and rejects a non-match; `transitive(dir, depth)` terminates on a **cyclic** call graph (recursion/mutual calls) at the depth cap (the DAG-name correction made concrete); every query result respects the row/snippet caps with a truncation marker. Manual: in a real `claude` session the `graph_*` tools appear (`/mcp`); `graph_find_symbol` + `graph_callers` answer correctly from the index; Opus's context grows by a short result, not file dumps.

**Phase G (semantic search)** — Unit: a `doc_chunk` embeds and round-trips through the CozoDB HNSW index; `graph_semantic_docs` returns the relevant chunk for a **paraphrased** query with no keyword overlap (where full-text misses it); **no embedder configured** → the tool runs full-text and labels itself a keyword fallback (and the tool is *not* advertised as semantic-capable); **embedded vectors present but endpoint removed** → still falls back to full-text (the query can't be embedded — proves the asymmetry is handled, not assumed); a configured model/dimension change **bumps the epoch**, kicks a re-embed, and ANN search is scoped to the current epoch so **mixed-epoch vectors are never compared**; the DB refuses to mix dimensions; the watcher re-embeds only changed chunks and **back-fills** ones skipped while the backend was down (and on first-ever endpoint configuration); a **partial-coverage** query returns results with a coverage note. ## Risks and Open Questions

- **Validation taken inline (no spike).** Unknowns surface during implementation: (a) **binary-size + build-time** impact of `cozo` + several C tree-sitter grammars (+ optional stack-graphs) in the portable release; (b) **full-index latency** on a large repo (is the first build seconds or minutes?) — drives whether lazy-background is enough or we need progress/cancel; (c) **query quality** — does tag-based resolution disambiguate overloads/shadows well enough to be trustworthy, or is stack-graphs needed sooner per language; (d) whether the **CozoDB SQLite backend** sustains the write throughput of a full build + the read concurrency of multiple consumers without lock contention.
- **stack-graphs is archived (Sep 2025).** The precise-resolution layer is a frozen dependency we may have to fork to update. Contained by keeping it *optional* behind the always-available tag layer — but if a grammar/tree-sitter version bump breaks the pinned `tsg` integration, we either pin tree-sitter older (affecting all grammars) or fork stack-graphs. Decide the version-pinning strategy early; the tag layer must stand alone if stack-graphs is dropped.
- **Resolution precision vs. breadth.** Tag-based refs are name-level — a call to `new()` or an overloaded method resolves to *a* `new`, not *the* one. For a navigation aid feeding an LLM this is usually fine (Opus disambiguates from context), but the tool results must **not overclaim precision** — label edges as resolved vs. name-only so Opus knows the confidence. Getting this labeling right is more important than chasing perfect resolution.
- **Incremental-update correctness (the hard part).** A code graph that silently drifts from the source is worse than none — Opus would trust stale callers. The watcher must reliably catch every edit (including external tools, branch switches, `git` checkouts), delete dangling edges on file removal, and the staleness check must repair edits made while closed. Branch switches that touch thousands of files must coalesce, not thrash. Failure mode to guard: a missed delete leaves a phantom symbol the agent "finds." Hash-based staleness verification on open is the backstop.
- **Per-project lifecycle in a multi-tab app.** cImp can have many tabs across several project roots open at once → several `GraphIndex`es + watchers live simultaneously. Bound the number kept warm (LRU-evict idle indexes, close their CozoDB handles + watchers), and define when an index is built/opened (on tab launch? on first `graph_*` call? on settings-enable?). Decide whether closing the last tab on a root tears its index down or keeps it warm for quick re-open.
- **`.cimp/` collisions + git hygiene.** Choose `.cimp/` carefully (confirm no existing convention clashes); ensure the gitignore recommendation is surfaced, not silently assumed — a committed multi-MB `graph.db` churning on every edit would be a bad first impression. Handle a read-only project dir (can't write `.cimp/`) by failing soft to in-memory/disabled with a clear status, not a crash.
- **Loopback channel coupling (inherits V8-03's surface).** Reusing `POST /graph/query` means graph queries share the offload loopback's auth/lifecycle. A stale discovery file or app-restart-mid-query must degrade to the read-only fallback cleanly (the V8-03 contract). Keep graph and offload ops cleanly separated on the endpoint so one can't wedge the other.
- **Doc↔code linking is fuzzy.** Linking a markdown paragraph or a doc-comment to "the symbol it describes" is heuristic (proximity, explicit references). Over-linking pollutes `graph_search_docs`; under-linking misses the connection. Start conservative (doc-comment→its symbol is exact; markdown→code is proximity + resolvable code-span references only) and treat broader semantic linking as the Phase-G/followup vector-search job.
- **Does Opus actually use the graph?** Like V8's offload nudge, adoption depends on the tool being discoverable and the injected guidance steering Opus to it for navigation tasks. Too weak → it keeps grepping; the tool descriptions + a short system-prompt addendum ("prefer `graph_*` for symbol/caller/import/doc lookups") must make the win obvious. This is the softest part of the design (same lesson as the V8 offload guidance).
- **Language coverage expectations.** Users will open repos in languages we don't index yet (Go, Java, C++, …) and get nothing. The status must clearly say "language not indexed" rather than implying an empty graph means an empty project. Make adding a grammar a documented, low-friction contribution path.
- **Embedding backend availability + drift (Phase G).** Semantic search needs a reachable embedder at **both** index time and query time — a query must be embedded into the same space as the chunks, so **stored vectors are useless when the endpoint is gone** (the "no embedder configured / removed" case). Handled by health-accurate tool advertising + transparent full-text fallback + the epoch scheme (see Decisions); the requirement here is that all of this stays **visible** (status readout shows embedder state, coverage %, epoch, backlog) and never silently returns stale or empty semantic results. **Residual drift the epoch can't catch:** the epoch keys on the model **id**, so swapping the GGUF behind the *same* model name (different weights, same id) yields silently mismatched vectors — mitigate by including any available model **fingerprint/hash** in the epoch where the endpoint exposes one, and always offer a manual **Rebuild embeddings**. Batch embedding calls to amortize round-trip latency over a full build. The user accepts that dedicating the 3070 to embeddings removes the V8 "fast" chat-offload tier.
- **What gets embedded — privacy + cost (Phase G).** Embedding sends doc/code text to the embedding box — the **same trust boundary as a V8 remote backend** (the user's own LAN host, not a cloud service, so code never leaves the user's control; if the endpoint were ever pointed at a cloud embedder, code *would* leave — document that). Embedding **code bodies** (vs. just docs + signatures) multiplies vector count and index size — keep it behind the `embed_code_bodies` sub-toggle and bound the chunk size.
- **First non-PTY tab — a new rendering path (Phase I).** Every existing tab is a PTY/xterm surface (Shell / AI / Offload Server); the Code Graph monitor is app-rendered, so the frontend tab host must branch on `TabKind` to mount a Svelte view vs. xterm without breaking the focus / lifecycle / persistence assumptions baked around terminal tabs. Audit the same surfaces the Offload Server tab touched (integrity check, close-others/all, drag-to-delete, active-tab logic) **plus** the render mount/unmount path — terminal-specific code (resize, scrollback, copy/paste, the `pty_write` wiring) must not assume an xterm instance that isn't there for this kind. It should **not** be saved into the user's `tabs[]` as a normal tab; reconcile it from `graph.enabled` like the reserved AI/Offload tabs.
- **Event-stream volume + UI cost (Phase I).** A from-scratch build or a full re-embed of a large repo emits thousands of events; pushing them raw would flood the IPC channel and thrash the dashboard. The throttled-snapshot (~2–4 Hz) + coalesced-activity-ring design has to hold under that load — measure it on a big repo, cap the activity-log ring, and **unsubscribe on tab blur** so an unfocused monitor costs nothing. The monitor is a read-of-live-state view; it must never become a write path or slow the indexer it observes (snapshot assembly off the hot path).
- **Orphan handles on hard-kill.** A taskkill/power-loss can leave a `graph.db` mid-write (CozoDB/SQLite WAL recovers on next open) and watchers dangling. Graceful exit closes handles + stops watchers; document the hard-kill caveat (same contract as scrollback/offload orphans) and verify CozoDB recovers a half-written DB on reopen (else rebuild-on-corruption).

## Followups (FUTURE-FEATURES candidates)

- **On-device / in-process embedding** — embed via `ort`/`fastembed` (a small `bge` model reusing the TTS/STT `ort` runtime) so semantic search needs no separate GPU box, for users without a spare card. Drops the remote embedding-endpoint dependency that Phase G ships with.
- **More languages with precise resolution** — Go/Java/C++/C# grammars + `tsg` rules (or rust-analyzer SCIP ingestion for precise Rust resolution beyond tags).

- **Graph-aware offload pre-pass** — the offload worker auto-consults the graph to scope a task ("which files define/use X") before grepping, cutting its own tool round-trips.
- **Shareable / prebuilt graphs** — commit or distribute a `graph.db` with a repo (opt-in), so teammates/CI get an instant index without a local build.
- **Refactoring/write operations** behind an explicit safety design (rename-symbol, find-and-edit-all-callers with diff preview + confirmation).
- **Visual graph explorer** — a cImp panel to browse the call/import graph (CozoDB's graph algorithms + a frontend renderer), turning the index into a navigation UI, not just an agent tool.
- **Cross-project federation** — query a dependency's graph, or a monorepo-wide union, behind an explicit multi-root model.
