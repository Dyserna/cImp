# Milestone V8-01: Local Task Offload (offload subtasks to a local LLM)

> **Release tag:** TBD by the user at ship time (V-series numbering is independent of the git tag, per the V6-01 convention). The "V8-01" label is a placeholder and opens a new feature pillar — *local compute offload* — distinct from the audio pillars (V6 STT, V7 voice cloning). Adjust the number freely at ship time.
>
> **Scope / sequel.** This milestone is the **single-local-backend core**. Remote/network/cloud backends + capability-aware routing + per-backend tool scoping are split into **[MILESTONE-V8-02](MILESTONE-V8-02-remote-backends-routing.md)**. V8-01 is built behind a minimal `Backend` seam so V8-02 is *additive*, not a retrofit.
>
> **No separate spike.** The dedicated Phase-0 validation spike was dropped by choice (user). The unknowns it would have answered are validated **inline during implementation** and flagged at the points where they bite (see Risks).
>
> **Motivation.** A single deep codebase search in the main Claude (Opus) session can burn 80%+ of the context window — the raw `grep`/file-read/tool-result bytes all pile into the cloud session's window. This milestone lets the main session **hand a self-contained subtask to a local LLM** (Qwen3.6-35B-A3B via `llama.cpp`'s `llama-server`) and get back **only the synthesized result**. The local model does the token-heavy churning — searching, reading, summarizing, web-fetching — and Opus's context grows by a paragraph instead of a megabyte.

## Purpose

Add an **offload worker** to cImp: a local-model agent that the main Claude Code session can call as an MCP tool. The user configures a `llama-server` command (binary + model + flags); cImp runs that server — surfaced as a read-only **Offload Server tab** — and exposes a single `offload_task` tool into every cImp-launched Claude tab. Opus calls it for offloadable work and receives a compact answer.

Everything stays **local and offline-capable** (the model and tools run on the user's machine). The agent loop, the MCP **server** (toward Claude), and the MCP **host/client** (toward the tool servers) are all in the cImp Rust binary — consistent with the [[project_constraints]] single-binary / no-Python preference, which governs *cImp's own binary*. The external dependencies are the user-provided `llama-server.exe` + GGUF and any optional MCP tool servers the user installs (e.g. `context7`, `git`, `fetch`, `filesystem`, `duckduckgo`) — those are user-managed optional services *like* `llama-server`, not bundled, so a Node/Python MCP server the user chooses to install does not violate the no-sidecar rule.

### Why this is an MCP tool, not a second tab

cImp already has a `claude-local` tab that points **Claude Code itself** at a local OpenAI/Anthropic-compatible endpoint (`claude_local` settings → `ANTHROPIC_BASE_URL` env). That is **not** what this milestone is. That swaps the brain of the *whole* session to a weak local model — it doesn't conserve the cloud session's context, it replaces the cloud session.

Offloading-to-conserve-context requires the opposite shape: the cloud Opus session stays in charge, but delegates a bounded subtask to a **subordinate local agent** whose intermediate tokens are invisible to it. The only place that delegation can live, in Claude Code, is an **MCP tool** the main session calls — `offload_task(instructions) → result`. Internally that tool runs a full agent loop (model ↔ tools) against the local server and returns one string. This is, in effect, a **local-model subagent**.

### How it fits the existing architecture

- **`llama-server` lifecycle** runs as a reserved, read-only **Offload Server tab** whose PTY *is* the server process (spawned via the existing Shell-launch path), so its load/progress output renders in the normal terminal view. Health-checked over HTTP, auto-restarted, and killed on app exit via the registry's existing `shutdown_all()`. Lazy-start / fail-soft follows the `stt`/`tts` engine pattern (construct on demand, never block launch).
- **HTTP client** reuses the existing `reqwest` dep (already in `Cargo.toml` for the usage tracker, `rustls-tls`, no system OpenSSL).
- **Config injection** reuses the `tabs/config.rs::build_pre_args` seam — the same place that injects `--append-system-prompt` (TTS) and `--settings` (status line). We add a Claude-only `--mcp-config <json>` pre-arg pointing Claude at our own `cimp --offload-mcp` subcommand, plus a system-prompt addendum telling Opus *when* to offload (the [[project_runtime_prompt_injection]] pattern). Like the status line, this is **session-scoped** — it never writes the user's `~/.claude` ([[project_statusline_context_bar]]).
- **The MCP server** is a new **hidden subcommand** `cimp --offload-mcp`, dispatched in `main()` before Tauri init exactly like `cimp --statusline` (`main.rs:67`). Single binary, no Node/Python sidecar.
- **Settings** add an additive `OffloadSettings` block with the established `#[serde(default)]` + redacted-`Debug`-for-secrets discipline (mirrors `ClaudeLocalSettings`, `schema.rs:519`).

## Architecture

```
  cImp (Tauri app, long-lived)
    └─ owns llama-server (Qwen3.6-35B-A3B) as the read-only "Offload Server" tab,
       reached over HTTP /v1 at 127.0.0.1:<port>  ◄───────────────────────┐
                                                                          │ OpenAI /v1 (tools)
  cImp-launched Claude tab (Opus)                                        │
    │  injected --mcp-config  → Claude spawns:                            │
    ▼                                                                     │
  cimp --offload-mcp   (per Claude session; MCP *server* toward Claude)  │
    │  tool: offload_task(instructions, context?, thinking?)              │
    │                                                                     │
    │  runs the AGENT LOOP (offload::agent):                              │
    │    ├─ POST /v1/chat/completions ─────────────────────────────────--─┘
    │    └─ routes each model tool_call ─► native tool  OR  MCP tool server
    │           (offload::mcp_host, MCP *client*) ─► context7·git·fetch·filesystem·ddg
    ▼
  returns ONE synthesized string ─► Opus   (all the loop's tokens stay local)

  ── Target variant (see Risks): the agent loop + the MCP-host pool move INTO the
     long-lived app (warm connections, one global concurrency semaphore, health-accurate
     capabilities); the --offload-mcp child becomes a thin loopback proxy. llama-server is
     the app-owned tab process in BOTH layouts.

  ── V8-02 generalizes the one llama-server to a backend POOL (local + remote/cloud) with a
     router. V8-01 is the single-local case, built behind a `Backend` seam.
```

- **The Tauri app always owns the one shared `llama-server`** — as the Offload Server tab's process (model-serving decision: *cImp spawns it*), reached over HTTP. One model load, shared by every Claude session.
- **cImp bridges two MCP roles.** Toward Claude it is an MCP **server** (exposes `offload_task`); toward the tool servers it is an MCP **host/client** (consumes their tools). `llama-server` never speaks MCP — cImp translates between the model's OpenAI-style `tool_calls` and each tool server's MCP `tools/call`.
- **Where the agent loop + MCP-client pool live is the one open decision (see Risks).** The `--offload-mcp` child is spawned per Claude session; MCP tool servers are stateful and slow to cold-start (`npx`/`uvx`). **MVP (diagram above):** the child runs the loop and spawns/connects its own tool servers for the duration of the call (simple, but pays cold-start per task, can't share a global concurrency counter, and reports capabilities from config). **Target:** the long-lived app owns the warm MCP pool and runs the loop; the child is a thin loopback proxy (warm connections, one global semaphore, health-accurate capabilities). Either way the child **never loads its own model** — `llama-server` is always the app-owned tab process reached over HTTP.

## Engine: Qwen3.6-35B-A3B via llama-server (decided)

**Chosen: `llama.cpp` `llama-server` serving Qwen3.6-35B-A3B (GGUF), spoken to over its OpenAI-compatible `/v1` API with `--jinja` tool-calling.** Rationale:

- **Qwen3.6-35B-A3B** is a Mixture-of-Experts model — **35B total params, ~3B active per token** (256 experts; 8 routed + 1 shared). Active-3B means it generates at small-model speed while reasoning at near-35B quality — exactly the profile for a latency-sensitive offload worker doing many tool-call round-trips.
  - **Hybrid attention** (alternating Gated DeltaNet + Gated Attention) keeps the **KV cache cheap at long context** — directly relevant to an offload worker that ingests large files/logs.
  - **262K native context (→ ~1M via YaRN)** means the local agent can swallow huge inputs that would never fit (or would be ruinously expensive) in the Opus window — the core context-saving lever.
  - **Thinking-by-default** (`<think>…</think>` reasoning) improves agentic tool use, but the agent loop must **strip `<think>` blocks from the final result** before returning to Opus, and reasoning adds output tokens/latency — managed by the Claude-controlled **dynamic-thinking** decision below (per-call `thinking` arg + per-step `auto` policy; cost validated during implementation).
  - **Multimodal** (text/image/video) is a bonus lever for a future "summarize this screenshot/diagram" tool — out of scope here but worth not designing against.
  - 500+ community GGUF quants exist for llama.cpp. Q4-class is roughly ~20 GB total weights (active-3B keeps *speed* high regardless of total size); fits a 24 GB GPU with the hybrid-attention KV savings, or CPU/partial-offload more slowly. *(The model path is configurable — the user can point at a coder-tuned or smaller quant.)*
- **`llama-server`** exposes `/v1/chat/completions` with **function/tool calling** when launched with `--jinja` (it applies the model's own chat template, including Qwen's tool-call format). cImp speaks plain OpenAI-style `tools` + `tool_calls` JSON — no bespoke protocol.
- **`reqwest`** (already present) is the only client dep. No new inference runtime in the binary; `llama-server` is an external, user-supplied executable.

> **Important reality:** `llama-server` does **not** itself execute tools, speak MCP, or do web search — it only *emits* `tool_calls` and waits for the caller to feed results back. The **agent loop that executes the tools lives in cImp** (`offload::agent`), and the **MCP-host that bridges to `context7`/`git`/`fetch`/`filesystem`/`duckduckgo` also lives in cImp** (`offload::mcp_host`). "The local model does web search" = the model *requests* a `search` tool, cImp routes it to the duckduckgo MCP server, and feeds the results back into the conversation.

## Decisions locked (from discussion)

- **Offload path = MCP tool for the main session.** cImp exposes a single `offload_task` tool via `cimp --offload-mcp`, injected into cImp-launched Claude tabs with `--mcp-config`. Returns only the synthesized result. *(The "managed local tab" alternative was rejected — it doesn't conserve context.)*
- **Tool surface = native baseline + configurable MCP servers.** Two layers:
  - **Native baseline (built into cImp, zero external deps)** so offload works with *no* tool servers installed:
    1. **`read_file`** — bounded reads (line range / max bytes) within an `allowed_root`.
    2. **`code_search`** — `grep`/`glob` across an `allowed_root`; matching paths + line snippets. *(Covers the deep-search case that motivated this.)*
  - **MCP tool servers (user-installed, aggregated by cImp's MCP host)** for the rich surface — discovered via each server's `tools/list` and exposed to the model as OpenAI tools:
    - **`duckduckgo`** — web search (no API key — this is the chosen web-search backend; the native-search-API question is closed).
    - **`fetch`** — URL → readable markdown.
    - **`filesystem`** — richer file ops (restricted to read tools + `allowed_roots` for safety; its write tools are not exposed this milestone).
    - **`git`** — read-only repo queries (log/diff/blame/show) for "when/why did X change" tasks.
    - **`context7`** — up-to-date, version-specific library/framework docs so the local model isn't reasoning from stale training data.
  - **`run_command`** (native, allowlisted, read-only) stays available for build/test/`git log`-style probes, gated by a command allowlist. The user enables exactly the MCP servers they want per the `offload.mcp_servers` config; nothing is assumed installed.
- **Web search = the `duckduckgo` MCP server.** No API key, no extra native HTTP backend.
- **One local backend, behind a `Backend` seam.** This milestone serves a single local `llama-server`, configured as a **command string** (`offload.server_command`, e.g. `llama-server --model …\Qwen3.6-35B-A3B-Q4.gguf --port 8080 --jinja -ngl 99 --ctx-size 150000 --flash-attn`) — the **source of truth** for model/quant/GPU-layers/context/host-port. cImp `shlex`-parses it (shlex is already a dep) to spawn, parses **host/port** + **`-np`** so it knows where to connect and how many slots exist, and **validates `--jinja` is present** (warns if missing — tool-calling needs it). cImp does **not** silently mutate the command. The agent/server code is structured behind a minimal `Backend` trait (one Local impl) so **V8-02** can add remote/cloud backends + routing without surgery. *(No GGUF auto-download this milestone — a followup.)*
- **Context window is discovered dynamically, never a separate setting.** After the server is healthy cImp `GET /props` and reads **`n_ctx`** — the authoritative window, correct regardless of `--ctx-size` vs `-c` vs default. The budget is re-read on every (re)start, so changing `--ctx-size` in the command and restarting just works. There is **no** `ctx_size` field to drift out of sync.
- **Parallel slots (`-np`) are parsed and respected — and they divide the context.** llama-server's `--parallel N` / `-np N` splits `--ctx-size` into N slots, so **each concurrent request gets only `n_ctx / N` tokens**. cImp parses `np` (default 1) from `server_command` and:
  - **Sets the per-request working budget to `(n_ctx / np) × high_water_pct`** — not the full window. (Confirm during implementation whether `/props` reports total `n_ctx` or already per-slot, so cImp divides only when it's the total.)
  - **Caps concurrent offload loops at `np`** — each in-flight loop owns one slot's worth of context, so ≤ `np` concurrent loops keeps the per-slot budget honest; excess `offload_task` calls **queue** (bounded by the timeout) rather than oversubscribe.
  - **Tracks in-flight count** and surfaces `in-flight / np` in the server tab + settings status.
  - **Tradeoff surfaced, not hidden:** real parallelism *and* a large per-request window means `--ctx-size = per_request_budget × np`, which costs KV/VRAM. The command is the user's to size; cImp just adapts the budget and concurrency to whatever `np`/`ctx` it finds.
- **Configurable per-task timeout.** `offload_timeout_secs` (a setting) bounds each `offload_task` wall-clock **including queue-wait for a slot** — on expiry the loop is cancelled and a clear timeout result is returned to Claude rather than hanging the tool call. (Promotes the loop's wall-clock cap to a real setting; a separate short connect/health timeout still guards a hung server.)
- **Feature toggles: `enabled` + `autostart`, plus Start/Stop/Reset.**
  - `enabled` (master, **default false**) — off = no server, no MCP-config injection into Claude tabs, `offload_task` not exposed.
  - `autostart` (**default false**) — when `enabled`, spawn `llama-server` on cImp launch and keep it warm. When off, it starts **lazily on the first `offload_task`** (or via a manual Start button), so a ~20 GB load never blocks launch.
  - **Reset / Restart** — because editing the command shouldn't reload ~20 GB on every keystroke, the command is applied **on demand**: edit freely, then click **Reset** to kill+respawn the process (re-health-check, re-read `n_ctx`/`np`). Pairs with explicit **Start**/**Stop**. Also the recovery path if the command is changed while cImp is running.
- **Context-budget management is first-class** (the discovered local window is the binding constraint, not Opus's — and it's *smaller* than Opus's). The agent loop must police the window or it silently overflows and llama-server truncates mid-task. Requirements:
  - **Work against the per-slot budget `(n_ctx / np) × budget_high_water_pct`** — reserve headroom for reasoning + the final answer (default ~80%; e.g. with `n_ctx`=150k and `np`=1 → ~120k working / ~30k reserved; with `np`=4 → only ~30k working per request — sizing the command is the user's call).
  - **Track real usage** from each response's `usage.prompt_tokens` (llama-server reports it) — no estimation.
  - **Hard-cap every tool result** (native *and* MCP-server outputs) with a truncation marker so the model knows it was cut and narrows/paginates instead of assuming full coverage.
  - **Compact at the high-water mark** — evict/summarize the oldest tool turns when usage crosses the threshold (a mini auto-compact for the sub-agent).
  - **Force final synthesis** when *any* of `max_steps` / `offload_timeout_secs` / token-budget is hit: "out of budget — answer from what you have now."
  - **Windowed reads + map-reduce** for inputs larger than the working budget: read tools take offset/limit so the agent summarizes chunk-by-chunk rather than holding a 300k-token file at once. *(This is what lets offload digest inputs that wouldn't even fit Opus — the per-call cap bounds a single call, while each `offload_task` gets a fresh budget and the loop can run map-reduce within it.)*
- **The `llama-server` runs as a reserved, read-only, non-closable "Offload Server" tab.** A new **system tab kind** whose PTY *is* the `llama-server` process (spawned from `server_command` via the existing Shell-launch path), so the user can watch **model-load progress and runtime logs** in the normal terminal view. Properties:
  - **Spawned inside a PTY** (portable-pty, already used) — llama.cpp detects the TTY and emits its richer progress/load output (ANSI/CR bars, GPU-offload lines, slot logs), rendered for free by the existing xterm.js + scrollback pipeline.
  - **Read-only** — no keystroke forwarding (`pty_write` is never wired for it), no paste/right-click-paste; selection/copy/scroll still work so the user can grab a log line.
  - **Non-closable** — no close affordance, not in the user-closable set, not draggable-to-delete; **it can only be removed by disabling the feature** (`offload.enabled = false`), which also stops the server. Materialized when `offload.enabled` (reconciled by the integrity check, analogous to `enabled_ai_tabs`); dropped when disabled.
  - **Lifecycle coordinated by the offload module, not the user** — autostart / Start / Stop / Reset drive this tab's process; health + `n_ctx` are still read over HTTP, independent of the PTY. A Stop/while-not-autostarted state shows a clear "server stopped — starts on first offload, or Start in settings" line rather than an empty terminal.
  - *(V8-02 remote backends have no tab — no local process to render — and appear only as a Settings status line. MCP tool-server consoles stay background → log this milestone; surfacing them as tabs is a followup.)*
- **Opt-in, off by default.** Both `enabled` and `autostart` are false on a fresh install — the feature spawns a multi-GB server and is useless without a configured command, so it's explicitly turned on (unlike TTS/STT which default on).
- **One shared host.** The Tauri app always owns the single `llama-server` (the Offload Server tab's process), reached over HTTP. The **agent-loop + MCP-client-pool location is the MVP/target split** (Risks): MVP runs both in the `--offload-mcp` child (own connections per call); target runs both in the app with the child as a loopback proxy. The child never loads its own model.
- **Per-call thinking is Claude-controlled (dynamic thinking).** `offload_task` takes an optional **`thinking: "auto" | "off" | "on"`** arg (default `auto`). Opus sets it per call from task shape — `off` for cheap deterministic work (extract/list/lookup), `on` for genuine analysis, `auto` to let the local agent decide. cImp's loop applies it per request via Qwen/llama.cpp's per-request thinking switch (`chat_template_kwargs:{enable_thinking:false}` / `/no_think` soft token / reasoning-budget — exact field confirmed during implementation), so one offload can think and the next can't against the same warm server.
  - **`auto` is per-step, not a coin flip:** think on the **planning** and **final-synthesis** turns, suppress on routine **tool-ingestion** turns — cuts the thinking tax across a multi-step loop without dumbing down the decisions that matter. `on`/`off` override this wholesale.
  - **Caveat (validate during impl):** disabling thinking may reduce **tool-calling reliability** for Qwen3. If it does, restrict `off` to **single-pass** tasks (summarize/extract, no tool loop) and keep at least planning-turn thinking for multi-tool offloads. The dynamic tool `description` should tell Opus when `off` is safe.
  - Pairs with the budget: thinking consumes the working window, so `thinking=off` on simple calls buys **both** latency and headroom.
- **Capabilities are reported to Claude dynamically.** The single `offload_task` tool would otherwise be opaque — Opus can't tell whether the local agent has web search, git, docs, etc. So cImp maintains a **capability registry** (native tools per their toggles + every MCP server currently **connected and healthy**, each mapped to a coarse capability label) and **renders the `offload_task` `description` from it on every `tools/list`**, e.g. "Available now: code search, file read, web search, url fetch, git history, library docs." When the set changes mid-session (a server crashes/recovers, a toggle flips), cImp emits **`notifications/tools/list_changed`** so Claude Code re-fetches and Opus sees the current capabilities — not a snapshot frozen at session start. The registry reflects **health, not just config** (a configured-but-down server is not advertised) — which is a concrete reason to favor the warm-pool target design, since the live child only knows what's configured at `tools/list` time, before any call. *(Alternative considered: several capability-scoped tools — `offload_research`/`offload_codebase`/… — advertised only when their backing servers are present. Cleaner-looking but re-imposes orchestration on Claude and fights the single-self-contained-delegation model; documented, not chosen.)* The **injected system-prompt addendum stays static** (how to use offload) — the *live* list lives in the tool description, since `--append-system-prompt` is fixed at tab launch and can't update mid-session.
- **Session-scoped injection.** Like the status line, the `--mcp-config` overlay and the offload system-prompt addendum apply only inside cImp-launched Claude tabs; `~/.claude` is never written.
- **Safety is explicit.** `run_command` runs only commands matching a configurable allowlist; native `code_search`/`read_file` and the `filesystem` MCP server are confined to configured `allowed_roots` (default: the launch project root). Only **read-class** MCP tools are exposed — write/edit/destructive tools from any server are filtered out this milestone.

## What This Milestone Delivers

Phases get **one offloaded task returning a real answer** as early as possible, then layer on tools, injection, settings UI, and packaging.

**Phase A — `llama-server` supervisor + the read-only Offload Server tab**

1. **Offload Server tab (the process owner).** Add a reserved system tab (`offload-server` id, new `TabKind::OffloadServer`) whose PTY *is* the `llama-server` process. The registry spawns it via the existing Shell-launch path from a `PtyLaunchSpec` built by **`shlex`-parsing `offload.server_command`** (program + args), so portable-pty hosts the process and the existing xterm.js/scrollback pipeline renders its load/progress output. The tab is **read-only** (no `pty_write` binding) and **non-closable** (not in the user-closable set; no close affordance). Materialized iff `offload.enabled` (integrity-check reconciled, like `enabled_ai_tabs`); removed when the feature is disabled.
2. `offload/server.rs` — `LlamaServer` (the single Local `Backend` impl) **coordinates the tab's process lifecycle and owns the HTTP view**: parse `--host`/`--port` (default `127.0.0.1:8080`) and **`-np`/`--parallel`** (default 1) from the command; warn if `--jinja` is absent; poll `GET /health` until ready; on ready **`GET /props` and cache `n_ctx`** (→ per-slot budget `n_ctx/np`); expose `base_url()`, `is_ready()`, `n_ctx()`, **`slots()`**, **`in_flight()`**, and **`restart()`** (tell the registry to kill+respawn the tab's PTY → re-health → re-read `n_ctx`/`np`); restart-with-backoff on *unexpected* exit. It does **not** spawn a second child — the tab's PTY is the one process. **Kill on app exit** is handled by the existing `registry.shutdown_all()` in the `CloseRequested` path. A **concurrency gate (semaphore sized to `np`)** admits ≤ `np` offload loops; the rest wait up to `offload_timeout_secs`.
3. Lifecycle driven by `enabled` + `autostart`: with `autostart`, spawn at launch; without, the tab shows a "stopped" line and the process starts **lazily on the first offload call** (or via the Start IPC) so a ~20 GB load never blocks launch. Stop/Start/Reset are explicit IPC commands (`offload_server_start` / `offload_server_stop` / `offload_server_restart`) that drive the tab's PTY. Fail soft: an empty/invalid command or a server that never reaches ready surfaces as a clear error in the tab + status indicator and on the first offload, never blocks launch (mirrors the STT lazy-engine pattern).

**Phase B — Agent loop + first tool, end-to-end via the MCP subcommand**

4. `offload/agent.rs` — the OpenAI-compatible loop: **acquire a concurrency permit** (≤ `np` in-flight; wait up to `offload_timeout_secs`); POST `messages` + the aggregated `tools` + `tool_choice: "auto"` to the server; parse `tool_calls`; dispatch each to its owner (native executor or MCP server); **token-cap each tool result** (with a truncation marker) before appending the `role: "tool"` message; repeat until a final assistant message or a cap is hit; **strip `<think>` blocks** and return the final text; release the permit. **Bounded by three caps — `max_steps`, `offload_timeout_secs` (incl. queue-wait), and the per-slot token budget `(n_ctx/np)`**: read `usage.prompt_tokens` from each response; when usage crosses the high-water mark, **compact** (evict/summarize the oldest tool turns); when any cap is hit, force a final-synthesis turn (or return a clean timeout result). Read tools accept offset/limit so the loop can **map-reduce** inputs larger than the working budget.
5. `offload/tools/{read_file,code_search}.rs` — the native baseline tools (highest value, zero external deps). `read_file` (bounded line/byte reads) and `code_search` (`grep`+`glob`) over `allowed_roots`, capped in size. These make offload work before any MCP server is installed.
6. `offload/mcp.rs` + `cimp --offload-mcp` subcommand — a minimal **stdio JSON-RPC 2.0 MCP server** (hand-rolled on `serde_json` + `tokio` stdio; `rmcp` is an option but hand-rolling keeps deps lean) implementing `initialize` (declare `tools.listChanged: true`), `tools/list`, `tools/call`. Exposes one tool: `offload_task(instructions: string, context?: string, thinking?: "auto"|"off"|"on") → string`, whose **`description` is rendered from the live capability registry** (native toggles + healthy MCP servers) at each `tools/list` and documents when to use each `thinking` mode. On call: read `settings.json` for the server `base_url` + tool/MCP config, run the agent loop, return the result. Dispatched in `main()` before Tauri init (mirror `--statusline`, `main.rs:67`).
7. **End-to-end:** manually register the MCP server in a real `claude` session and confirm `offload_task("find all call sites of X and summarize")` returns a synthesized answer while cImp's `llama-server` does the searching via the native tools.

**Phase C — MCP host (aggregate the user's tool servers)**

8. `offload/mcp_host.rs` — an MCP **client** that, per `offload.mcp_servers` config, spawns/connects each server (stdio via `command`+`args`, or HTTP), runs its `initialize`+`tools/list`, and namespaces its tools (e.g. `ddg__search`, `git__log`). At loop time the host merges native + MCP tools into the `tools` array and routes each `tool_call` to the owning server's `tools/call`. **Read-class filter:** only expose read/query tools; drop write/edit/destructive ones (esp. `filesystem`/`git`). Confine `filesystem` to `allowed_roots`. Maintain a **capability registry** of healthy servers→capability labels and, on any health/membership change, signal `offload/mcp.rs` to emit `notifications/tools/list_changed` (re-rendering the `offload_task` description). *(In the MVP self-contained child the registry is config-derived; in the warm-pool target it reflects live health.)*
9. Wire the **decision from Risks** on where the pool lives — MVP: the `--offload-mcp` child owns the connections for the call; target: the Tauri app owns a warm pool and the child proxies to it.
10. `offload/tools/run_command.rs` — native, allowlisted, read-only: execute a command **only if it matches `command_allowlist`**, in an `allowed_root`, with a timeout and truncated captured output. Deny by default. *(Web search/fetch/docs/git now come from the `duckduckgo`/`fetch`/`context7`/`git` MCP servers — no native `web.rs` needed.)*

**Phase D — Injection (wire it into cImp-launched Claude tabs)**

11. `tabs/config.rs::build_pre_args` — when `offload.enabled`, append Claude-only `--mcp-config <json>` pointing at `cimp --offload-mcp` (reuse the status line's forward-slash / 8.3-short-path command resolution from `statusline::launch_command`). The MCP config JSON: `{"mcpServers":{"cimp-offload":{"command":"<cimp>","args":["--offload-mcp"]}}}`.
12. Append an **offload system-prompt addendum** via the existing `--append-system-prompt` mechanism (or merged into the TTS instructions): tell Opus *when* to offload — "For broad codebase searches, large-file/log summarization, or web research, prefer calling `offload_task` to conserve context; pass a self-contained instruction and expect a synthesized result." Without this nudge Opus won't reach for the tool. Gated by an `offload.inject_guidance` toggle.

**Phase E — Settings surface**

13. `OffloadSettings` (Phase F schema) surfaced in Settings: **`enabled`** + **`autostart`** toggles; a **`server_command` text field** with **Start / Stop / Reset** buttons (Reset = restart with the current command) and a live **server status + discovered `n_ctx`/`np`/per-slot budget + `in-flight / np`** readout; a **budget/limit group** (`budget_high_water_pct`, `per_tool_result_token_cap`, `max_steps`, `offload_timeout_secs` — note: **no `ctx_size`/`np` fields**, both discovered from the command/`/props`); native-tool toggles, `allowed_roots` editor, `command_allowlist` editor; and a **MCP-servers editor** (per server: name + `command`/`args` or URL + enable). A "Test offload" button runs a canned task. Status indicators reuse the bottom-bar conventions.

**Phase F — Schema, deps, docs**

14. `settings/schema.rs` — `OffloadSettings` with `#[serde(default)]` and redacted `Debug` for any secret (env-passed MCP API keys). Fields: **`enabled: bool`** (default false), **`autostart: bool`** (default false), **`inject_guidance: bool`** (default true — the Phase-D system-prompt nudge), **`server_command: String`** (the single source-of-truth llama-server command, shlex-parsed at spawn), **`tools: OffloadToolToggles`** (native `read_file`/`code_search`/`run_command` on/off), **`allowed_roots: Vec<PathBuf>`** (default: launch project root), **`command_allowlist: Vec<String>`**, **`mcp_servers: Vec<McpServerConfig>`**. `McpServerConfig { name, command, args, env, url, enabled }` mirrors Claude's own `mcpServers` shape so users can paste familiar config. **Budget/limit fields:** `budget_high_water_pct` (~80%), `per_tool_result_token_cap` (~8k), `max_steps`, **`offload_timeout_secs`** (per-task wall-clock incl. queue-wait) — **no `ctx_size`/`np`** (discovered at runtime, not stored). Additive — no schema-version bump needed (matches the status line's additive landing). *(V8-02 generalizes `server_command`+`autostart` into a `backends: Vec<OffloadBackend>` list via a small additive migration.)*
15. `Cargo.toml` — likely **no new deps** (reuse `reqwest`, `serde_json`, `tokio`, `which`, `shlex`); reconsider `rmcp` (official Rust MCP SDK) only if hand-rolling **both** the MCP server and the MCP client proves fiddly — the client side (host) is the more involved half and is where `rmcp` would pay off.
16. Docs: `DESIGN.md` (offload in the feature list + the architecture diagram), `README.md` (how to point at a `llama-server` + model, how to add MCP tool servers, what gets offloaded, safety/allowlist notes), `MAINTENANCE.md` (recommended `llama-server` flags / model variants / example MCP-server configs), `CHANGELOG.md` (Added: local task offload). No model ships in the release zip (user-supplied).

## What This Milestone Does NOT Do

- **Remote / network / cloud backends + capability-aware routing + per-backend tool scoping.** Deferred to **[MILESTONE-V8-02](MILESTONE-V8-02-remote-backends-routing.md)**. V8-01 serves one local backend (behind the `Backend` seam).
- **Bundle or auto-download the model or MCP servers.** User supplies `llama-server` + GGUF, and installs whichever MCP tool servers they want. Auto-download (~20 GB GGUF, resume/verify) and a one-click MCP-server installer are tracked followups.
- **Write/edit tools.** The offload agent is **read-only** (search/read/web/docs/git-read/allowlisted-run). Write/edit/destructive tools are filtered out even when a server (e.g. `filesystem`, `git`) offers them. Editing offload is a deliberate future decision with its own safety design.
- **Replace the cloud session or the `claude-local` tab.** Opus stays the driver; `claude-local` is unrelated and stays as-is.
- **Per-tab / per-project offload models.** One shared server, global config — consistent with the [[project_global_only_avatar_tts]] global-only posture for app-wide services.
- **Stream partial offload results** back into Opus. The tool returns one final string per call (an MCP tool result). Progress is logged/shown in cImp, not streamed into the cloud transcript.
- **Auto-decide offloading without the prompt nudge.** Whether Opus offloads is driven by the injected guidance + Opus's judgment; there's no interception/routing layer.

## Test Plan

**Phase A (supervisor + tab)** — Unit: `shlex`-parse of `server_command` yields the expected program+args (incl. tricky Windows paths/quoting); host/port + `-np` extraction; `--jinja`-absent warning; health-poll transitions `stopped → starting → ready`; `n_ctx` is read from `/props`; an immediate child exit surfaces an error, not a hang. Manual: enable offload → the **Offload Server tab appears**, is **read-only** (typing does nothing, no paste), has **no close button**, and shows live model-load progress; server reaches ready; kill it externally → supervisor restarts and the tab keeps streaming; **disable the feature → the tab disappears and the process stops**; quit cImp → no orphan `llama-server`.

Manual: in a real `claude` session, `offload_task("find call sites of X, summarize")` returns a coherent answer; cImp logs show the local agent's `code_search` round-trips; Opus's context grew by only the result; firing two offloads with `np=1` shows one running + one queued in the status.

**Phase C (tools)** — Unit: `code_search` respects `allowed_roots` (a path outside is refused); `read_file` clamps to the byte/line cap; `run_command` refuses a non-allowlisted command and honors the timeout. Manual: web_search+fetch returns readable text for a live query (with the `duckduckgo`/`fetch` servers configured); an allowlisted `cargo test` runs and its output is summarized.

**Phase D (injection + capability reporting)** — Unit: `build_pre_args` adds `--mcp-config` only for `claude` and only when `offload.enabled` (Aider/other binaries get nothing — mirror the existing status line tests in `config.rs:255`); the injected command path is forward-slashed (Git Bash gotcha); the rendered `offload_task` description lists exactly the healthy native+MCP capabilities and updates when one is toggled/dropped. **Phase E/F (settings, build)** — Manual: every `OffloadSettings` field persists across restart; an old `settings.json` without the block loads with the feature off (additive default); MCP API keys never appear in logs (redacted `Debug`). ## Risks and Open Questions

- **Validation taken inline (no spike).** The dedicated Phase-0 spike was dropped by choice, so the stack's unknowns are validated *during* implementation and surface as build-time issues rather than before: (a) Qwen3.6-35B-A3B emitting **reliable `tool_calls`** through llama-server's `--jinja` OpenAI shim across many turns; (b) **end-to-end loop latency** being worth it vs. doing the work in Opus; (c) whether `/props` `n_ctx` is **total or per-slot** under `-np`; (d) the **per-request thinking flag** and whether **thinking-off breaks tool-calling**; (e) VRAM headroom at the chosen quant/`--ctx-size`. Accepted risk: if tool-calling proves flaky or the loop too slow, the feature's value is in question — caught in Phase B rather than a spike.
- **Thinking-mode tax — mitigated by Claude-controlled dynamic thinking.** Qwen3.6 reasons in `<think>` blocks by default — better decisions, but more output tokens and latency per step, multiplied across a loop. Mitigations in the design: the `thinking` arg on `offload_task` (Opus picks per call), the per-step `auto` policy (think only on planning/synthesis), and stripping `<think>` from the returned result. Residual: (a) confirm the quant/llama.cpp build honors the per-request thinking flag; (b) **thinking-off may degrade tool-calling** — if so, `off` is gated to single-pass tasks. Thinking also **consumes the token budget** — factor it into the headroom reserve.
- **Hard local context cap (≈150k on the dev box, VRAM-bound) — discovered, not assumed.** The window is set by the user's `--ctx-size` in `server_command` and read back authoritatively from `/props` (`n_ctx`); it is *smaller* than Opus's and is the binding constraint on any single `offload_task`. The agent must self-police it (track `usage.prompt_tokens`, cap tool results, compact at the high-water mark, map-reduce oversized inputs, force final synthesis on cap) — see the context-budget decision. Failure mode if ignored: llama-server silently truncates the conversation mid-task and the model answers from a half-window. Confirm during implementation what `--ctx-size` actually fits in VRAM alongside the ~20 GB weights at the chosen quant — KV (even with hybrid attention) plus weights sets the real cap, and that number lives in the command with cImp adapting automatically.
- **Parallelism vs. per-request context (the `-np` trap).** `-np N` quarters (or worse) each request's usable window — easy to misconfigure into "150k context" that's really 30k per request, then watch tasks truncate. cImp must derive the per-slot budget from `np` and make the real per-request number visible in Settings. Concurrency tracking/gating is only globally correct in the warm-pool design (one shared semaphore); independent MVP children can't share a counter, so they'd rely on the server's slot queue and report only per-child in-flight — document that limitation. Also: a request that exceeds `offload_timeout_secs` while *queued* (never got a slot) must return a distinct "busy/timeout" result so Opus can retry later rather than assume the task failed.
- **Command parsing pitfalls.** `server_command` is user free-text: cImp must `shlex`-parse it robustly (Windows paths with spaces/backslashes, quoting), find host/port, and not choke on flags it doesn't recognize. If `--jinja` is missing, tool-calling silently won't work — validate and warn rather than failing obscurely. If the command names a port already in use, surface a clear bind error.
- **Dynamic capability reporting depends on client behavior.** The plan leans on Claude Code honoring `notifications/tools/list_changed` (re-fetching `tools/list` and re-surfacing the updated `offload_task` description mid-session) — verify it actually does, and how promptly. Even at session start the description must be accurate, so capability health has to be known by the time `tools/list` is answered: trivial in the warm-pool design (the app knows live health), but the MVP self-contained child can only report *configured* servers before its first call — document that gap, or have the child do a fast health-probe of configured servers at startup. Keep the description concise (a one-line capability list), not a dump of every namespaced tool.
- **Offload Server tab vs. the tab model.** It's the first **read-only, non-closable, system-owned** tab — existing code assumes tabs are user-closable Shell/AI tabs. Audit the integrity check, layout/persistence (it shouldn't be saved as a user tab or dragged into a delete), close-others/close-all actions, and the focused-tab/active-tab logic so the new kind is handled everywhere. It's reconciled from `offload.enabled`, not stored in the user's `tabs[]` the way builtins are — decide whether it lives in `tabs[]` (like reserved AI builtins) or is injected at materialization; the former reuses more machinery. Restart (Reset) tears down and re-creates the PTY — the tab must survive that (show "restarting…"), not vanish.
- **Where the MCP-client pool lives (open design decision).** MVP (self-contained `--offload-mcp` child spawning its own tool-server connections per call) is simple but pays `npx`/`uvx` cold-start every task; target (Tauri app owns a warm pool, child proxies over loopback) is faster but adds an internal IPC surface. Start MVP, measure cold-start cost, promote to the pool if it hurts. *(V8-02's global concurrency counter + health-accurate capabilities also favor the pool.)*
- **Does Opus actually offload?** The behavior depends entirely on the injected guidance + Opus's judgment. Too weak a nudge → it never offloads; too strong → it offloads things it should keep. Tune the addendum; consider examples in the prompt. This is the softest part of the design.
- **MCP servers are an external surface.** Each is a user-installed `npx`/`uvx` process — versions drift, a server can hang or crash, and several are Python/Node (fine as user-managed services, but they widen the dependency/footprint story). The host must time-out and isolate a misbehaving server (one bad tool server must not wedge the whole offload), and surface per-server health in Settings.
- **`run_command` + `filesystem`/`git` are the main safety surface.** `run_command` is allowlist-only, read-only-intent, confined to `allowed_roots`, timed out, output-capped. MCP servers that expose write/destructive tools (`filesystem` write, `git` commit) have those tools **filtered out** by the read-class filter, and `filesystem` is confined to `allowed_roots`. Default everything conservative and document it loudly; a misconfigured allowlist or an unfiltered server tool is the risk to watch.
- **VRAM / fallback.** ~20 GB Q4 weights need a capable GPU; the hybrid-attention KV cache stays small even at long context (a real advantage here), but on smaller GPUs `llama-server` spills to CPU and the loop gets slow. Expose `-ngl` (in the command) and document the tradeoff; the status indicator should make "running slowly on CPU" visible.
- **Orphan processes.** A hard-killed cImp (taskkill/power loss) can leave `llama-server` **and** spawned MCP servers running. The `CloseRequested` path kills them on graceful exit; document the hard-kill caveat (same contract as scrollback persistence) and consider a best-effort orphan sweep on next launch.
- **Coupling when the host isn't ready.** If offload is invoked before `llama-server` (or a required MCP server) is up, the child returns a clear "offload not ready — enable/start it in cImp settings" error rather than silently loading its own model. Decide whether the child may *request* a start (loopback signal) or simply fail.
- **Single binary, three roles.** `cimp` is now a Tauri GUI, an MCP **server** subprocess (`--offload-mcp`, toward Claude), **and** an MCP **host/client** (toward the tool servers). The `--offload-mcp` path must stay GUI-free and fast to spawn (launched per Claude session), exactly like `--statusline`.
